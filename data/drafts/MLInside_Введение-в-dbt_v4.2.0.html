ELT вместо ETL: почему трансформации переехали в хранилище

  • Storage и compute разъехались и подешевели
  • Сырьё грузим как есть, переделка — новый SELECT
  • Практики нужны вокруг SQL, а не вокруг движка
  • ETL остаётся там, где сырое класть нельзя
 ETL   T до загрузки
       ─ схема фиксируется заранее
       ─ переделка = перезагрузка

 ELT   T после загрузки
       ─ сырьё лежит целиком
       ─ переделка = новый SELECT

[~1.5 мин] Главное: ELT победил не потому, что «так модно», а потому что в облачных хранилищах пересчитать дешевле, чем перезагрузить.

Рассказ: схема слева — вся разница в одной строке: где стоит буква T. В ETL трансформация происходит до загрузки, значит схему целевой таблицы надо придумать заранее, и любая ошибка в модели данных лечится повторной загрузкой из источника. В ELT сырьё уже лежит в хранилище целиком, и переделка модели — это просто новый SELECT поверх того же сырья.

Картинка справа показывает то же самое как архитектуру: источники слева, дальше развилка ELT/ETL, хранилище в центре, а потребители — ML, BI, приложения — справа. Обратите внимание на нижний ряд: governance, quality, catalog — это то, что появляется поверх, когда трансформаций становится много.

Для MLE: для признаков это принципиально. Определение признака меняется чаще, чем схема источника; при ELT смена определения — правка SQL и пересчёт, а не переговоры с командой загрузки.

Осторожно: не объявлять ETL устаревшим. Там, где нельзя класть сырое (персональные данные, лицензионные ограничения, дорогой объём) или где источник — поток с обогащением на лету, T по-прежнему стоит до загрузки.

Переход: «У этого сдвига был свой манифест. Он короткий и до сих пор актуальный».

dbt: восемь инженерных свойств слоя трансформаций

  • Version control — SQL-модель лежит в git, как и код обучения
  • Modularity — модель ссылается на модель, а не копирует её текст
  • Testing — данные проверяются контрактом до того, как их увидит модель
  • Documentation — определение признака, владелец, семантика поля
  • Lineage — виден граф: от source до training dataset
  • Incremental — не пересчитываем всю историю признаков
  • CI — изменение SQL проходит ревью и автотесты
  • Orchestration — сборка встраивается в общий production-пайплайн

[~1.5 мин] Главное: правила слоёв держатся ровно до первого дедлайна. Поэтому их проверяют машинно, а не договорённостью.

Рассказ: пройти по левой колонке схемы — это пять типовых нарушений, каждое из которых встречается в любом проекте старше полугода.

`mart → source` — витрина сходила в сырьё напрямую. Работает, пока источник не поменял тип колонки; после этого падает не staging (где это было бы видно), а витрина в проде.

`join` в staging — самое дорогое. Гранулярность там никто не проверяет, потому что слой «простой», а строка после джойна уже не одна на заказ.

`int → int → int` — цепочка промежуточных моделей без явного смысла. Каждая по отдельности понятна, вместе они нечитаемы.

`view → view → view` — вьюха на вьюхе. Для BI-запроса раз в день это ничего не стоит; для витрины признаков, которую читают на каждой сборке обучающей выборки, это часы compute.

Для MLE: картинка справа — канонический вид слоёв из документации dbt. Держите её как эталон и сравнивайте со своим `models/`: если каталог не раскладывается на эти три группы, слои у вас на бумаге, а не в проекте.

Осторожно: нарушение бывает осознанным. Правильный ход — не отключать правило, а оформить исключение (в `dbt_project_evaluator` это seed), чтобы для всех остальных моделей правило продолжало работать.

[~2.5 мин] Главное: это не конкурс «какой подход правильный», а четыре разных ответа на вопрос что считать единицей модели данных.

Рассказ: быстро по строкам, по одной фразе на подход.

Medallion (bronze / silver / gold) пришёл из мира Databricks и хорош ровно одним: его понимают за минуту. Но он ничего не говорит о том, как моделировать внутри уровня, — это словарь зрелости, а не метод.

Классический EDW по Кимбаллу — факты и измерения вокруг бизнес-процесса. Сильная сторона — понятность для аналитика; слабая — переделка измерений при изменении источника.

Data Vault решает ровно эту боль: hub (бизнес-ключ), link (связь) и satellite (атрибуты с историей) разделены, поэтому новый источник добавляется рядом новым сателлитом, а существующие таблицы не переписываются. Руками такой SQL не пишут — его генерирует AutomateDV по метаданным. Подробности — в Part 3.

Activity Schema — самый интересный для нас. Вся модель сводится к одной широкой таблице активностей: `entity_id`, `ts`, `activity`, плюс полезная нагрузка. Признаки из неё считаются оконными функциями по времени, а point-in-time получается почти бесплатно — потому что у каждой строки уже есть момент события. В ClickHouse это ложится идеально: одна `MergeTree` с `ORDER BY (entity_id, ts)`.

Для MLE: в контексте ClickHouse и признаков сравнение сводится к двум строкам. Kimball удобен, когда вокруг вас BI. Activity Schema удобнее, когда вокруг вас события и оконные признаки, — а у ML-задач это чаще так.

Осторожно: не выбирать подход под красоту схемы. Data Vault для одного продуктового источника — оверинжиниринг; Activity Schema для финансовой отчётности — мучение.

Переход: «Посмотрим, что из этого реально стоит взять под ML-витрину».

Что брать под ML: raw и витрина под задачу

два решения: raw без моделирования · витрина под ОДНУ задачу
-- RAW: только объявление, ноль логики
sources:
  - name: olist_raw          # схема 1:1 с источником
    tables: [orders, order_items, sellers]

-- ACTIVITY-подобный промежуточный слой: одна строка = одно событие
{{ config(materialized='incremental',
          engine='MergeTree()',
          order_by='(seller_id, activity_ts)') }}
select seller_id                        as entity_id,
       order_delivered_customer_date    as activity_ts,
       'order_delivered'                as activity,
       delay_days                       as value
from {{ ref('stg_orders') }}
where order_delivered_customer_date is not null

-- ПРИЗНАК: оконный срез по этой таблице — point-in-time почти бесплатно
select entity_id,
       avgIf(value, activity_ts <  o.order_purchase_timestamp
                and activity_ts >= o.order_purchase_timestamp - interval 90 day)
         as seller_avg_delay_90d
from {{ ref('int_seller_activity') }}

[~2 мин] Главное: два решения, которые определяют всё остальное: raw кладём без моделирования и витрину делаем под задачу, а не про запас.

Разбор кода: три блока. Первый — объявление source: схема один к одному с источником, никакой логики. Второй — промежуточный слой в духе Activity Schema: одна строка = одно событие продавца, ключ сортировки `(entity_id, activity_ts)`. Третий — признак поверх него: оконный срез с ограничением сверху по моменту заказа.

Обратить внимание на третий блок: условие point-in-time здесь пишется одной строкой, потому что у каждого события уже есть его собственный момент. В классической раскладке за это же отвечает отдельная модель с self-join — мы её увидим в блоке про инкрементальность.

Для MLE: правило про витрину «под задачу» проговорить отдельно. Соблазн собрать одну большую `mart_all_features` есть всегда. Через квартал в ней будет сорок колонок, из которых используются семь, а поддерживать придётся все сорок: каждая — обязательство перед проде. Правильный ход — общий intermediate со всеми событиями и тонкие витрины поверх, по одной на модель.

Пример: Olist — `mart_delivery_features` под задачу просрочки. Появится задача про отток продавцов — это отдельная витрина поверх того же `int_seller_activity`, а не ещё десять колонок в существующей.

Осторожно: raw «как есть» не означает «без контроля». Freshness и тесты на ключи ставятся именно на source — но это проверки, а не преобразования.

staging: чистка и производные поля

  • Один источник — одна staging-модель, без соединений
  • Здесь появляются типы, флаги и части даты
  • Доставленным считаем по НАЛИЧИЮ даты, а не по статусу
  • NULL там, где «неизвестно» — не подменяем нулём
models/staging/stg_orders.sql
{{ config(materialized='view') }}

select
  order_id,
  customer_id,
  order_status,
  order_purchase_timestamp,
  order_delivered_customer_date,
  order_estimated_delivery_date,

  toHour(order_purchase_timestamp) as order_hour,
  toDayOfWeek(order_purchase_timestamp) as order_dow,

  -- «неизвестно» ≠ «вовремя»
  case
    when order_delivered_customer_date is null
      then null
    when dateDiff('day',
           order_estimated_delivery_date,
           order_delivered_customer_date) > 0
      then 1
    else 0
  end as is_late_delivery

from {{ source('olist_raw', 'orders') }}

[~1 мин] Главное: staging — это место, где сырые данные становятся пригодными к употреблению, и единственное место, где это делается.

Разбор кода: показать две вещи. Первая — `toHour`/`toDayOfWeek`: временные признаки считаются один раз здесь, а не в каждой витрине. Вторая — блок `case` с `null`: у 2 965 заказов Olist нет даты доставки, и мы честно ставим NULL.

Не разбирать: перечисление колонок сверху.

Для MLE: это ваш таргет. `is_late_delivery` = 1, если приехало позже обещанного. NULL означает «исход неизвестен» — такие строки из обучающей выборки надо исключать явно, а не молча считать их «вовремя».

Пример: два заказа в Olist имеют `order_status = 'delivered'` без даты доставки. Если определять доставленность по статусу, они попадут в выборку с непонятным таргетом.

Осторожно: подмена NULL нулём — самая частая тихая ошибка на этом слое. Доля просрочек сразу занижается, и модель учится не тому.

Переход: «Дальше — соединения. Это следующий слой».

intermediate: заказ ровно одной строкой

  • Позиции сворачиваем ДО соединения — иначе join размножит строки
  • Все соединения LEFT — 775 заказов не имеют позиций
  • Гранулярность названа в имени модели и проверена тестом

with items as (
  -- сначала свернули до заказа,
  -- только потом соединяем
  select
    order_id,
    count(*)                  as item_count,
    count(distinct seller_id) as seller_count,
    sum(price)                as items_value,
    sum(freight_value)        as freight_value
  from {{ ref('stg_order_items') }}
  group by order_id
)

select
  o.*,
  coalesce(i.item_count, 0)    as item_count,
  coalesce(i.seller_count, 0)  as seller_count,
  coalesce(i.items_value, 0)   as items_value,
  coalesce(i.freight_value, 0) as freight_value,
  d.customer_seller_distance_km
from {{ ref('stg_orders') }} as o
left join items as i using (order_id)
left join {{ ref('int_order_distance') }} as d
       using (order_id)

[~1.5 мин] Главное: одна строка = один заказ. Это утверждение, за которое модель отвечает и которое проверяется тестом.

Разбор кода: показать CTE `items` и сказать вслух: свёртка до соединения. Если сначала сджойнить позиции, а потом группировать — заказ из пяти позиций даст пять строк, и любая метрика «по заказам» поедет.

Вторая точка — `left join`. Не `inner`. 775 заказов Olist не имеют ни одной позиции; inner тихо выбросил бы их и занизил и выручку, и долю просрочек.

Для MLE: `coalesce(..., 0)` здесь корректен: «позиций нет» действительно означает ноль позиций. Сравните со слайдом про staging, где ноль был бы ложью. Решение про NULL принимается по смыслу поля, а не по привычке.

Осторожно: «размножение строк джойном» — ошибка, которую почти невозможно заметить глазами. Ловится тестом `dbt_utils.equal_rowcount` против `stg_orders`.

Jinja, макросы и пакеты

[~0.3 мин] Главное: блок про переиспользование.

Рассказ: «Как перестать копипастить SQL между двадцатью моделями и не превратить проект в магию».

Jinja: от копипасты к переиспользуемому слою

  • Jinja — шаблонизатор: dbt рендерит модель ДО отправки в базу
  • Отсюда всё: ref(), source(), config(), is_incremental()
  • Цена: SQL в редакторе больше не равен SQL в базе
  • Поэтому дальше показываем обе половины
 models/*.sql (SQL + Jinja)
          ↓  dbt compile
 target/compiled/… (чистый SQL)
          ↓  dbt run
 таблица или вью в базе

[~1 мин] Главное: Jinja — это ещё один шаг сборки между вашим файлом и базой. Пока вы это помните, всё остальное просто.

Рассказ: объяснить схему в три фразы: файл модели — это шаблон; `dbt compile` превращает его в обычный SQL; в базу уезжает результат. `ref()` и `config()` — не магия dbt, а обычные функции Jinja-контекста.

Картинка справа — маленький, но показательный пример: `{{ 'order_date' if target.name == 'prod' else 'created_at' }}`. Одна модель, две разные колонки в двух окружениях. В редакторе это не SQL; SQL из этого получится только после компиляции.

Для MLE: аналогия — препроцессор или шаблон Helm. Тот же выигрыш и та же опасность: удобно, пока читаемо.

Осторожно: правильная рамка — это инструмент, который позволяет одному инженеру держать переиспользуемый слой трансформаций, а не «ещё одна возможность dbt».

Переход: «Смотрим на конкретных конструкциях — и сразу на то, во что они компилируются».

[~2 мин] Главное: одна и та же модель по-разному собирается в dev и в проде — и это описано в коде, а не в инструкции. Ниже черты видно, во что именно она превратилась.

Разбор кода: четыре точки в верхней половине. `var('train_window_days', 180)` — окно обучения стало параметром: поменять его можно флагом `--vars`, не трогая SQL. `env_var('CH_RAW_DB', ...)` — то же самое, но значение приходит из окружения: адрес базы и креды в git не попадают. Цикл `for st in [...]` — два почти одинаковых агрегата пишутся один раз. `if target.name == 'dev'` — в dev-профиле модель собирается на срезе.

Дальше — нижняя половина, ради которой слайд и сделан. Цикла нет: он развернулся в два `countIf`. Условия нет: `target.name` был `dev`, значит `limit` остался. `ref` стал именем таблицы, `var` стал числом 180. В базу уезжает обычный SQL — никакой Jinja там не существует.

Не разбирать: `{%-` и `-%}` — это управление пробелами, скажите одной фразой «минус съедает пробел» и идите дальше.

Для MLE: параметризованное окно — это ровно то, что нужно для экспериментов с признаками: собрать витрину на 90 и на 365 днях, не заводя две модели.

Пример: `dbt build --select mart_seller_orders --vars '{train_window_days: 365}'` — и в скомпилированном SQL станет `interval 365 day`.

Осторожно: значения `var()` идут в SQL как текст. Не подставляйте туда пользовательский ввод.

Переход: «А если один и тот же кусок логики нужен в пяти моделях — это уже макрос».

Макрос: повторяющаяся логика признака

  • Макрос возвращает фрагмент SQL, а не значение
  • Хороший кандидат — то, что уже написано дважды
  • safe_divide: деление, которое не падает и не даёт inf
  • Ниже черты — во что вызов превратился: обычный case, никакой магии
  • Поменяли решение про ноль — правка в одном файле, а не в пяти моделях
macros/safe_divide.sql → target/compiled/…
-- ИСХОДНИК: макрос
{% macro safe_divide(num, den) -%}
  case when {{ den }} = 0 then null
       else {{ num }} / {{ den }} end
{%- endmacro %}

-- и его вызов в витрине признаков
select order_id,
  {{ safe_divide('freight_value',
                 'total_price') }} as freight_share
from {{ ref('int_order_level') }}

-- ────── СКОМПИЛИРОВАНО ──────

select order_id,
  case when total_price = 0 then null
       else freight_value / total_price
  end as freight_share
from analytics.int_order_level

[~1.5 мин] Главное: макрос — это DRY для SQL. Не «продвинутая фича», а способ не разъехаться в определении признака.

Разбор кода: верхняя половина — тело макроса (обычный `case`, обёрнутый в `{% macro %}`) и его вызов. Нижняя — то, что реально уехало в базу: вызов исчез, на его месте стоит развёрнутый case. Проговорить вслух: макрос не существует во время выполнения запроса, он существует только во время компиляции.

Потом сказать главное: если завтра решим, что при нулевом знаменателе нужен не NULL, а ноль — правка в одном месте, и она автоматически приедет во все модели, которые вызывают макрос.

Не разбирать: `-%}` и `{%-`.

Для MLE: доля стоимости доставки и отношение просрочки к обещанному сроку — оба признака делят одно на другое, оба ломаются на нуле. Без макроса это два разных `case`, которые через полгода будут вести себя по-разному.

Пример: та же логика нужна и в staging позиций, и в витрине по категориям. Продублируете — границы разъедутся.

Осторожно: макрос — не место для бизнес-смысла. `safe_divide` — про арифметику; «что считать просрочкой» должно остаться видимым в модели.

Переход: «Второй полезный класс макросов — ключи и окна».

Макрос: суррогатный ключ и повторяющееся окно

  • Суррогатный ключ — стабильный хеш от набора колонок
  • Нужен там, где естественного ключа нет — например, заказ × продавец
  • Повторяющееся временное окно тоже стоит вынести в макрос
  • Ниже черты видно цену абстракции: пакетный макрос разворачивается в длинный хеш
  • Правило: prefer readable SQL — абстрагируем паттерны, а не каждые три строки
macros/ → target/compiled/… (ClickHouse)
-- ИСХОДНИК
select
  {{ dbt_utils.generate_surrogate_key(
       ['order_id', 'seller_id']) }} as order_seller_key
from {{ ref('stg_order_items') }}
where {{ lookback_window('order_purchase_timestamp') }}

{% macro lookback_window(ts, days=90) -%}
  {{ ts }} >= now() - interval {{ days }} day
{%- endmacro %}

-- ────── СКОМПИЛИРОВАНО ──────

select
  lower(hex(MD5(concat(
    coalesce(cast(order_id  as String), '_dbt_utils_null'), '-',
    coalesce(cast(seller_id as String), '_dbt_utils_null')
  )))) as order_seller_key
from analytics.stg_order_items
where order_purchase_timestamp >= now() - interval 90 day

[~1.5 мин] Главное: абстрагировать стоит повторяющиеся инфраструктурные паттерны, а не каждые три строки SQL.

Разбор кода: верх — два вызова: `generate_surrogate_key` из dbt_utils и свой макрос окна. Низ — во что это развернулось. Обратить внимание на длину скомпилированного хеша: пакетный макрос честно приводит каждую колонку к строке, подставляет заглушку вместо NULL и склеивает через разделитель. Руками это писать никто не станет, и в этом весь смысл.

Второй макрос проще: если завтра «окно наблюдения» станет 120 дней, правка в одном файле, а в скомпилированном SQL поменяется число.

Не разбирать: почему именно MD5 и почему `_dbt_utils_null` — это деталь реализации пакета.

Для MLE: суррогатный ключ нужен, когда гранулярность составная. В Olist пара «заказ × продавец» естественного ключа не имеет, а группировать по ней надо.

Осторожно: сформулировать правило вслух и записать его на следующем слайде: prefer readable SQL. Макрос, который экономит две строки, но требует открыть третий файл, — это чистый убыток. Нижняя половина слайда — как раз аргумент в обе стороны: она и оправдывает макрос, и показывает, что читать после компиляции придётся вот это.

Разбор кода: `not_null` + `unique` на `order_id` — это машинная запись фразы «одна строка на заказ». `expect_column_values_to_be_between` с `min_value: 0` — счётчик не может быть отрицательным. `relationships` — каждый заказ витрины существует в intermediate.

Осторожно: dbt-тесты — это assertions, а не физические constraints. dbt выполняет запрос и смотрит, есть ли строки-нарушители. В базе никакого ограничения не появляется, и данные, нарушающие тест, физически лежат в таблице. Тест ловит их, а не запрещает.

Lineage: два вопроса и один граф

  • Граф строится сам — из ref() и source()
  • «Откуда взялось» — вверх по графу: +модель
  • «Что сломается» — вниз по графу: модель+
  • exposure добавляет в граф то, что живёт вне dbt
селекторы графа — те же и в docs, и в CI
# от чего зависит витрина признаков

# кто пострадает, если её тронуть
dbt ls --select mart_delivery_features+

# собрать модель вместе со всем ниже
dbt build --select stg_orders+

[~1.5 мин] Главное: lineage в dbt не описывают, его выводят. Граф — побочный продукт того, что вы писали `ref()` вместо имени таблицы.

Рассказ: показать картинку справа — обычный lineage-граф из `dbt docs`: слева источники, дальше staging, справа витрины. Стрелки нарисовал не человек.

Дальше два селектора слева, и это главное, что нужно унести. `+модель` — вверх: от чего она зависит, откуда пришли данные. `модель+` — вниз: кто её читает и что сломается. Один и тот же синтаксис работает в `dbt ls` для анализа, в `dbt build` для сборки и в CI для Slim CI.

Для MLE: третий пункт — про `exposure`. Обученная модель, дашборд или витрина, которую читает внешний сервис, живут вне dbt, и граф про них не знает. Объявленный exposure втаскивает их в тот же граф, и вопрос «кто пострадает» получает полный ответ. Разберём его в блоке дополнительных возможностей.

Пример: перед правкой `stg_orders` полезно выполнить `dbt ls --select stg_orders+` и увидеть, что от неё зависит семнадцать моделей и одна обучающая выборка.

Дальше `dbt build`. Это не `dbt run`: команда собирает модель и тут же прогоняет её тесты, идя по графу. Модель, чей тест упал, считается сломанной, и всё, что от неё зависит, пропускается — это встроенное поведение, его не надо программировать.

Дальше решение оркестратора: тесты зелёные → идём в обучение; красные → останавливаемся и шлём алерт, а в проде продолжает работать предыдущая версия модели.

Внизу схемы — второй барьер, `evaluate_model`: даже на чистых данных модель может выйти хуже текущей. Это разные отказы, и точки останова у них разные.

Для MLE: самый дорогой сценарий в ML-проде — не упавший пайплайн, а молча переобученная на битых данных модель. Упавший пайплайн заметят за час. Просевшую метрику — через неделю, в лучшем случае.

Пример: ingestion привёз половину заказов за день. Тест `equal_rowcount` красный → training не стартовал → в проде работает вчерашняя модель. Именно это и нужно.

Осторожно: нижняя строка схемы. Различайте `severity`: часть проверок должна быть `warn`, иначе команда быстро научится игнорировать красное. Блокирующими делайте те, что действительно ломают обучение.

Переход: «Добавим тесты и документацию на нашу сквозную схему».

Инкрементальность, ClickHouse и point-in-time

[~0.3 мин] Главное: самый ML-специфичный блок лекции.

Рассказ: «Как обновлять признаки дёшево — и как при этом не отравить обучающую выборку».

Инкремент вместо полного пересчёта

  • Full refresh: пересобираем витрину целиком, читая всю историю
  • Incremental: дописываем только новую дельту
  • is_incremental() истинно только когда таблица уже существует
  • {{ this }} — сама целевая таблица модели
  • unique_key превращает вставку в upsert изменившихся строк
models/marts/mart_delivery_features.sql
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='append') }}

select *
from {{ ref('int_order_level') }}

{% if is_incremental() %}
  -- учебный вариант: только новее
  -- максимума в самой витрине
  where order_purchase_timestamp > (
    select max(order_purchase_timestamp)
    from {{ this }}
  )
{% endif %}

[~2 мин] Главное: инкремент — это про деньги и время сборки, и именно поэтому в feature layer он почти обязателен.

Разбор кода: три точки. `materialized='incremental'` — материализация. `is_incremental()` — блок работает только при повторных прогонах; при первом запуске и при `--full-refresh` он выключен и модель собирается целиком. `{{ this }}` — ссылка на саму целевую таблицу.

Не разбирать: `incremental_strategy` — про стратегии скажем на слайде про ClickHouse.

Для MLE: посчитайте на пальцах. Витрина признаков за три года — это сотни миллионов строк и джойны. Полный пересчёт каждую ночь стоит часы compute; инкремент за сутки — минуты. Разница уходит прямо в счёт за кластер.

Пример: первый прогон Olist собирает всю историю; дальше — только новые заказы.

Осторожно: этот фильтр — учебный, а не production-паттерн. Он написан ровно так, как его пишут в первый раз, и ровно так же ломается. Почему — следующий слайд, это важно.

Переход: «Разберём, что именно здесь сломается».

Ловушка: WHERE ts > max(ts)

  • Corrections — строку в источнике поправили задним числом

  • Во всех трёх случаях фильтр по максимуму данные просто не увидит
  • Хуже всего: пайплайн зелёный, тесты зелёные, витрина неверна

[~1.5 мин] Главное: `WHERE ts > max(ts)` предполагает, что данные приходят строго по возрастанию времени события. В проде это почти никогда не так.

Рассказ: три сценария. Первый — опоздание: событие произошло восьмого, а доехало одиннадцатого; максимум в витрине уже двенадцатое, и строка не попадёт никогда. Второй — исправление: заказ пятого марта переоформили, дата события не изменилась, фильтр его не поднимет. Третий — изменяемый источник: у заказа Olist статус и дата доставки дописываются позже, чем он был создан.

Подчеркнуть худшее свойство этой ошибки: она молчаливая. Тесты проверяют то, что в таблице есть; отсутствующие строки они проверить не могут.

Для MLE: для обучения это означает систематическое смещение. Опоздавшие заказы — это чаще всего именно проблемные заказы. Выбросив их, вы обучаете модель на выборке, где просрочек меньше, чем в реальности.

Осторожно: не превращать это в «инкремент — зло». Инкремент нужен; неверна конкретная стратегия отбора дельты.

Переход: «Как делать правильно».

Watermark, lookback и идемпотентность

  • Считаем по времени ЗАГРУЗКИ или по окну, а не по максимуму факта
  • lookback — перекрываем окно назад, чтобы поднять опоздавшее
  • unique_key + delete+insert — повторный прогон не плодит дубли
  • Идемпотентность: два прогона подряд дают одинаковый результат
  • Партиции: пересобрать день целиком часто дешевле, чем искать дельту
models/marts/mart_delivery_features.sql
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='delete+insert') }}

select * from {{ ref('int_order_level') }}

{% if is_incremental() %}
  -- окно с перекрытием: сутки инкремента
  -- плюс lookback на опоздавшие и правки
  where order_purchase_timestamp >=
        (select max(order_purchase_timestamp)
         from {{ this }})
        - interval {{ var('lookback_days', 7) }} day
{% endif %}

[~2 мин] Главное: дельта считается с перекрытием, а повторная запись обязана быть безопасной.

Разбор кода: две строки. `incremental_strategy='delete+insert'` вместе с `unique_key` означает: перед вставкой строки с такими же ключами удаляются. Второй прогон на тех же данных даёт тот же результат — это и есть идемпотентность. И `- interval lookback_days day`: мы сознательно перечитываем последние семь дней, чтобы поднять опоздавшее и исправленное.

Не разбирать: как именно ClickHouse исполняет delete+insert.

Для MLE: lookback — это компромисс, который вы обязаны выбрать осознанно. Семь дней стоят в семь раз дороже одного и покрывают опоздания до недели. Ответ на вопрос «сколько» даёт не интуиция, а распределение задержки между временем события и временем загрузки в ваших данных.

Пример: ещё надёжнее — партиционирование. Витрина партиционирована по месяцу; пересобираем затронутые партиции целиком. Никакой дельта-логики, полная воспроизводимость, цена — перечитанная партиция.

Осторожно: идемпотентность надо проверять. Прогон дважды подряд и сравнение `count()` — минимальный тест, который ловит большинство ошибок инкремента.

Переход: «Теперь про специфику движка — у нас ClickHouse».

[~3 мин] Главное: правильно посчитанный SQL-агрегат может быть неверным признаком. Для ML недостаточно корректной арифметики — нужна корректность по времени.

Рассказ: разобрать пример медленно, он того стоит. Мы предсказываем просрочку заказа X, оформленного первого марта в десять утра. Один из признаков — средняя просрочка этого продавца.

Наивный SQL: `avg(delivery_delay_days) group by seller_id`. Он посчитает среднее по всем заказам продавца, которые есть в таблице, — включая заказы C и D, которые завершились после первого марта. В момент предсказания этой информации не существовало.

Модель на такой выборке покажет отличные метрики на валидации и просядет в проде. Классическая утечка: признак несёт информацию из будущего.

Для MLE: правило формулируется одной строкой и должно висеть у вас перед глазами: feature_timestamp <= prediction_timestamp. Любой агрегат по истории обязан быть ограничен сверху моментом предсказания.

Пример: в Olist это особенно коварно, потому что `order_delivered_customer_date` дописывается в ту же строку заказа позже. Таблица выглядит так, будто всё было известно сразу.

Осторожно: нижняя часть схемы — самое практичное на слайде. Утечка не ловится обычными dbt-тестами: `not_null` и `unique` на такой витрине зелёные, потому что запрос синтаксически корректен и данные целы. Ловится она ревью SQL (ищем верхнюю грань в join-е), аномально хорошей метрикой на валидации и бэктестом на замороженной дате.

Переход: «Смотрим, как это выражается в SQL».

Point-in-time на SQL: история продавца

models/intermediate/int_seller_delay_history.sql
{{ config(materialized='table') }}

with order_seller as (                    -- продавец заказа
  select order_id, min(seller_id) as seller_id
  from {{ ref('stg_order_items') }} group by order_id
),
history as (                              -- ЗАВЕРШЁННЫЕ заказы продавцов
  select os.seller_id,
         o.order_delivered_customer_date                  as done_at,
         dateDiff('day', o.order_estimated_delivery_date,
                         o.order_delivered_customer_date) as delay_days
  from {{ ref('stg_orders') }} as o
  join order_seller as os using (order_id)
  where o.order_delivered_customer_date is not null
)
select
  cur.order_id,
  avg(h.delay_days) as seller_avg_delay_90d,
  count(h.done_at)  as seller_orders_90d
from {{ ref('stg_orders') }} as cur
join order_seller as cs using (order_id)
left join history as h on h.seller_id = cs.seller_id
      -- ВОТ ЭТИ ДВЕ СТРОКИ И ЕСТЬ POINT-IN-TIME
      and h.done_at <  cur.order_purchase_timestamp
      and h.done_at >= cur.order_purchase_timestamp - interval 90 day
group by cur.order_id

[~2 мин] Главное: point-in-time — это два условия в JOIN, а не отдельная технология.

Разбор кода: показать ровно две строки, помеченные комментарием. Верхняя — строго раньше момента покупки: берём только то, что было известно. Нижняя — окно 90 дней назад: не тащим всю историю, признак должен быть про недавнее поведение.

Обратить внимание: ключевое условие стоит на дате завершения (`done_at`) исторического заказа, а не на дате его покупки. Заказ, купленный в феврале и доставленный в апреле, на первое марта ещё не был завершён — и в среднее входить не должен.

Не разбирать: CTE `order_seller` (у заказа может быть несколько продавцов, берём одного) и производительность self-join. На больших объёмах это переписывают через оконные функции или asof-join, идея не меняется.

Для MLE: именно эту модель и её описание мы видели на слайде про docs. Круг замкнулся: ML-свойство признака зафиксировано и в SQL, и в документации.

Осторожно: `left join`, а не `inner`. У первого заказа продавца истории нет — признак должен стать NULL, а сам заказ обязан остаться в выборке. `inner join` тихо выбросил бы всех новых продавцов, а это как раз самый рискованный сегмент.

Переход: «Мы дошли до края зоны ответственности dbt. Проговорим границу явно».

Для MLE: это полезный слайд для разговора с руководством. Когда предлагают «а давайте всё в dbt», ответ — вот граница, и она проведена по природе задач, а не по вкусу. Формулировка для запоминания в нижней строке: dbt отвечает за таблицы, ML-стек — за модель.

Осторожно: ошибка бывает в обе стороны, и вторая встречается чаще. Считать dbt «просто SQL-раннером» и не пользоваться тестами, документацией и графом — значит платить за инструмент и не получать главного.

Переход: «Третий вопрос, который всегда задают: а Python внутри dbt можно?»

Python-модели в dbt: escape hatch, а не замена SQL

  • Поддержаны на Snowflake (Snowpark), Databricks (PySpark), BigQuery (BigFrames)
  • ClickHouse и Postgres Python-моделей не дают — это ограничение адаптера
  • Модель — функция model(dbt, session), возвращает ровно один DataFrame
  • ref() и source() доступны через объект dbt — модель встаёт в общий DAG
  • Ограничения: только table/incremental, нет view и ephemeral
  • print() не виден, импорт функций между Python-моделями невозможен
models/marts/mart_seller_cluster.py
def model(dbt, session):
    dbt.config(materialized="table",
               packages=["scikit-learn"])

    orders = dbt.ref("int_order_level")

    from sklearn.cluster import KMeans
    pdf = orders.to_pandas()
    pdf["cluster"] = KMeans(
        n_clusters=5, n_init=10
    ).fit_predict(
        pdf[["distance_km", "item_count"]]
    )
    return pdf

[~1.5 мин] Главное: Python в dbt — это аварийный выход, а не альтернативный основной путь.

Разбор кода: четыре строки. `def model(dbt, session)` — обязательная сигнатура. `dbt.config(packages=[...])` — зависимости объявляются здесь, а не в requirements проекта. `dbt.ref(...)` — тот же граф зависимостей, что и в SQL: Python-модель встаёт в общий DAG наравне с SQL-моделями. `return pdf` — модель обязана вернуть ровно один DataFrame.

Не разбирать: параметры KMeans, они тут для правдоподобия.

Для MLE: и сразу трезвая оговорка. На ClickHouse, с которым мы работаем в этом курсе, Python-моделей нет — это ограничение адаптера, а не настройка. Поддержка есть у Snowflake, Databricks и BigQuery. Проверяйте страницу конфигурации вашего адаптера, прежде чем закладывать это в архитектуру.

Осторожно: несколько практичных ограничений. `print()` в логах dbt не появится — код исполняет платформа, а не dbt. Функции из одной Python-модели нельзя импортировать в другую. И материализация только `table` или `incremental` — ни `view`, ни `ephemeral`.

Переход: «Разберём, какой именно Python имеется в виду — pandas или Spark, и почему это разные истории».

Где исполняется Python: pandas и Spark

  • pandas в dbt-модели — это данные, вытянутые из хранилища В ПАМЯТЬ платформы
  • to_pandas() на витрине признаков за три года — способ убить сессию
  • На Snowflake и BigQuery «pandas» — это Snowpark/BigFrames DataFrame, ленивый
  • Spark (Databricks) — единственный вариант, где Python масштабируется как SQL
  • PySpark-модель исполняется кластером, а не одним узлом — pandas там опция, не норма
  • Правило: агрегации остаются в SQL, Python берёт только то, чего в SQL нет

def model(dbt, session):

    return df.group_by("seller_id").agg(

# PySpark (Databricks) — считает кластер
def model(dbt, session):
    df = dbt.ref("int_order_level")
    return df.groupBy("seller_id").avg("delay_days")

# pandas — ВСЁ приезжает в память одного узла
def model(dbt, session):
    pdf = dbt.ref("int_order_level").to_pandas()
    #     ↑ вот здесь и больно
    return (pdf.groupby("seller_id")["delay_days"]
               .mean().reset_index())

[~2 мин] Главное: «Python-модель» — это три разные вещи в зависимости от платформы, и различает их где физически лежат данные в момент вычисления.

Разбор кода: три блока делают одно и то же — среднюю просрочку по продавцу.

Первый, Snowpark: `df` — ленивый DataFrame, `group_by` превращается в SQL, считает склад. Данные из хранилища не уезжают.

Второй, PySpark на Databricks: `df` — распределённый DataFrame, считает кластер. Это единственный из трёх вариантов, где Python масштабируется так же, как SQL.

Третий, pandas: `to_pandas()` — и вся таблица приезжает в память одного процесса. Для сотни тысяч строк Olist это нормально; для витрины признаков за три года это отказ.

Для MLE: отсюда практическое правило, которое стоит записать. Агрегации не выносят в pandas. pandas берут там, где нужна библиотека, которой нет в SQL, и берут на уже свёрнутых данных — на выходе агрегата, а не на входе.

Пример: кластеризация продавцов в Olist — это сотни строк после свёртки. Такой pandas безопасен. Тот же KMeans по позициям заказов — это 112 650 строк и растущая история, и его надо считать иначе.

Осторожно: на ClickHouse ни один из трёх блоков не заработает — Python-моделей адаптер не поддерживает. Способ обойти это без смены платформы — следующий слайд.

Рассказ: проговорить критерий каждой строки.

SQL — по умолчанию. Сигнал простой: вы можете описать нужный результат как SELECT, не рассуждая о порядке обработки строк. Если можете — пишите SQL, он дешевле, переносимее и попадает в граф.

Не dbt — когда задача не про создание таблицы в хранилище. Это самая дорогая ошибка из трёх: попытка затащить обучение или сервинг в dbt превращает его в плохой оркестратор и плохой сервер одновременно. Обучение живёт в оркестраторе рядом с dbt, а не внутри него.

  • Философия обратная: не Airflow с dbt внутри, а dbt, из которого генерируется Airflow

from airflow.decorators import dag, task
from cosmos import DbtTaskGroup, ProjectConfig, RenderConfig

@dag(schedule="0 3 * * *", catchup=False, tags=["olist", "ml"])
def olist_delivery_model():
    wait_raw = FileSensor(task_id="wait_for_olist_raw", filepath=RAW_MARKER)

    transform = DbtTaskGroup(            # весь dbt-граф раскроется в задачи
        group_id="dbt_olist",
        project_config=ProjectConfig(dbt_project_path=DBT_DIR),
        profile_config=PROFILE,
        render_config=RenderConfig(select=["tag:features"]),
    )

    @task
    def train():                         # обучение — уже НЕ dbt
        df = read_features("analytics.mart_delivery_features")
        return fit_and_log(df)           # метрики → tracking

    @task.short_circuit
    def evaluate(run_id: str) -> bool:   # барьер качества модели
        return metrics(run_id)["roc_auc"] >= baseline()

    run = train()
    wait_raw >> transform >> run
    evaluate(run) >> register(run)

Разбор кода: четыре точки. Первая — `DbtTaskGroup`: три конфига, и весь граф моделей раскрылся в задачи. Никаких `stg_orders >> int_order_level` руками. Первое — секреты. Пароль и адрес хранилища приходят переменными окружения из хранилища секретов CI; в репозитории лежит только `profiles.yml` с `env_var()`. Ни одна строка кредов не коммитится.

Второе — отдельный target `ci`. Сборка идёт в свою схему, а не в прод. Это не формальность: без этого упавший PR оставляет мусор в продовой схеме.

Третье — порядок: `dbt deps` перед сборкой, всегда. Забытый `deps` — самая частая причина «в CI не работает, а локально работает».

Переход: «Как сделать барьер быстрым: собираем только изменённое».

Slim CI: пересобираем только изменённое

  • state:modified+ — изменённые модели и всё, что от них зависит
  • --defer со --state: недостающие ссылки читаются из прод-схемы
  • Нужен свежий manifest.json прод-прогона как артефакт пайплайна
  • Минуты вместо часов — и барьер перестают отключать «на разок»
  • В dbt v2 сравнение с прошлым состоянием стало частью движка (dbt State)
  • Устаревший манифест деградирует молча — обновлять его должен прод-пайплайн

📚 Материалы: Node selection · defer

[~2 мин] Главное: Slim CI — это ответ на вопрос «как сделать обязательный барьер таким, чтобы его не отключили». Экономика простая: полная сборка витрин на каждый PR занимает часы.

Разбор кода: два флага. `--select state:modified+` — dbt сравнивает текущий проект с манифестом прошлого прогона и берёт изменённые модели плюс всех их потомков. `--defer --state` — всё остальное, чего в CI-схеме нет, читается из прода вместо пересборки.

Внизу — варианты селектора. Полезнее всего `1+state:modified+`: он добавляет одного родителя сверху, потому что тесты на связь между слоями иначе не с чем сравнивать.

Для MLE: проверка занимает ровно столько, сколько вы реально тронули. Правка одного признака — сборка одной витрины, а не всего проекта.

Осторожно: `state:modified` сравнивает с манифестом прошлого прогона. Если артефакты устарели или потерялись, сравнение молча деградирует, и в сборку попадёт не то, что вы ожидали. Обновление артефактов — часть прод-пайплайна, а не отдельная забота дежурного.

Пример: в dbt Core v2 механика состояния стала частью движка и работает быстрее — про это есть слайд в Part 3.

[~2.5 мин] Главное: команд немного, и запоминать надо не их, а модификаторы — почти вся работа с dbt в проде это `--select` плюс один флаг.

Рассказ: взять четыре строки, остальные студент прочитает.

dbt build — главная. Она собирает модель и тут же прогоняет её тесты, идя по графу; `--fail-fast` останавливает прогон на первом падении, что в CI экономит минуты.

dbt retry — недооценённая. Она повторяет последний прогон с той точки, где он упал, читая `run_results.json`, а не начинает с нуля. На ночной сборке из пятидесяти моделей, упавшей на сорок седьмой, это разница между тремя минутами и часом. Работает без аргументов — состояние берётся из `target/`.

dbt test --store-failures — записывает нарушившие строки в отдельную таблицу вместо того, чтобы просто сказать «упало N строк». Для отладки признаков это то, что нужно: можно посмотреть глазами, какие именно заказы сломали контракт.

dbt compile — первый инструмент отладки Jinja, мы им пользовались весь блок про шаблоны.

Для MLE: практический набор на каждый день — четыре строки: `dbt build -s <модель>+`, `dbt retry`, `dbt test -s <модель> --store-failures`, `dbt compile -s <модель>`.

Осторожно: `--full-refresh` на инкрементальной витрине признаков за три года — это полный пересчёт истории. Он иногда нужен, но это не «на всякий случай».

[~2 мин] Главное: плюс — это направление по графу. Справа от имени — вниз, к потребителям; слева — вверх, к источникам. Всё остальное запоминается само.

Разбор кода: три группы. Первая — способы назвать модель: по имени, по тегу, по пакету, по каталогу, по файлу. Тег — самый практичный: пометьте `tag: features` все модели витрины признаков, и ночная сборка описывается одной строкой.

Вторая — граф. `my_model+` собирает модель и всех её потомков: это то, что вы запускаете после правки. `+my_model` — модель и всех её родителей: это то, что вы запускаете, когда собираете витрину с нуля в чистой схеме. `+my_model+` — обе стороны. Цифра перед плюсом ограничивает глубину.

Третья — комбинации: пробел работает как ИЛИ, запятая как И, `--exclude` вычитает.

Картинка справа — как это выглядит в терминале: dbt печатает, сколько моделей нашёл, какие стартовали, что создано (view или table) и сколько это заняло. Строку `Done. PASS=… WARN=… ERROR=… SKIP=…` читают в первую очередь — SKIP означает, что выше по графу что-то упало.

Для MLE: после правки признака запускайте `dbt build -s <модель>+`, а не `dbt build`. Разница — секунды против получаса, и вы точно видите, что именно затронуто.

Осторожно: тот же синтаксис используется в Slim CI (`state:modified+`), поэтому привычка ставить плюс в правильную сторону окупается дважды.

Переход: «Селекторы дают контроль над сборкой. Теперь — контроль над качеством самого проекта».

Качество проекта: dbt_project_evaluator

  • Шесть групп правил: граф, тесты, документация, структура, производительность, governance
  • Ловит нарушения слоёв — join в source мимо staging, rejoin, fanout, модели без потомков

[~2 мин] Главное: слои и правила из начала лекции держатся ровно до первого дедлайна. dbt_project_evaluator — это автоматическая проверка тех самых договорённостей.

Рассказ: он проверяет шесть групп правил: устройство графа (join в source мимо staging, rejoin уже соединённых сущностей, fanout, модели без потомков), покрытие тестами и документацией, структуру (именование и раскладка по каталогам), производительность (цепочки вьюх там, где нужна таблица) и governance.

Ключевая деталь — формат результата. Это не текстовый отчёт, который прочитают один раз: пакет собирает `fct_`-модели с нарушениями и обычные dbt-тесты поверх них, поэтому его можно поставить в CI и завалить сборку. Таблица `int_all_dag_relationships` отдаёт весь граф строками, и по ней пишутся собственные правила обычным SQL.

Про исключения — важно. Если нарушение осознанное, оно оформляется строкой в seed-е, и правило продолжает действовать для всех остальных моделей, а не отключается целиком.

Для MLE: рядом стоят ещё три инструмента, и они закрывают разное. dbt-score (pip, не dbt-пакет) оценивает метаданные модели по правилам и выдаёт балл 0–10 — на этом строят гейт «описания и владельцы обязательны». elementary ловит аномалии объёма и свежести и держит историю прогонов. audit_helper сравнивает старую и новую версию витрины — это ровно то, что нужно после рефакторинга признака.

Осторожно: ставить evaluator на зрелый проект без подготовки — значит получить триста нарушений и закрыть вкладку. Правильный ход — включить одну группу правил, починить, включить следующую.

Переход: «Ещё один инструмент отладки, про который вспоминают в три часа ночи, — логи».

📝 Логирование в dbt

  • Пишется в stdout и в файл logs/dbt.log — путь задаётся --log-path или DBT_LOG_PATH
  • Форматы text · debug · json, отдельно для консоли (--log-format) и файла (--log-format-file)
  • Уровни debug|info|warn|error|none; -d включает DEBUG в консоли
  • JSON-события несут info и data, а также node_info: имя модели, статус, материализация

Разбор кода: четыре блока.

Первый — разные форматы для человека и для машины. В консоль идёт читаемый `text`, в файл — `json` с уровнем `debug`. Это единственный способ одновременно нормально смотреть за сборкой и иметь полный след для разбора.

Второй — `DBT_ENV_CUSTOM_ENV_*`. Любая переменная окружения с этим префиксом автоматически попадает в `info.extra` каждого события. Отсюда получается связь между прогоном dbt и запуском в оркестраторе: положили туда id пайплайна — и любое падение теперь трассируется до конкретного DAG-рана.

Третий — `jq` по json-логу: имя модели, статус, время старта. То же самое, но без ручного чтения.

Четвёртый — про автоматизацию: у `dbt ls` с версии 1.5 уровень по умолчанию `INFO`, и в скрипт приезжает шапка. Лечится `--quiet` или `--log-level warn`.

Для MLE: три места, куда смотреть при разборе падения. `target/compiled/` — что получилось из шаблона. `target/run/` — что именно ушло в базу вместе с DDL. `logs/dbt.log` — все запросы и ответы движка. В таком порядке.

Осторожно: `--log-level debug` пишет в лог полные тексты запросов. На проде это и объём, и возможная утечка значений в логи — уровень для файла выбирают осознанно.

Переход: «Ещё несколько возможностей, которые редко попадают в базовый рассказ, но регулярно нужны».

Дополнительные возможности: exposures, contracts, groups

  • exposure — потребитель ВНЕ dbt: дашборд, ML-модель, сервис. Втаскивает его в граф
  • Отвечает на вопрос «кого предупредить», который иначе решается перепиской
  • Попадает в dbt docs и в селекторы: dbt ls --select +exposure:delivery_delay_model
  • contract: enforced — схема витрины фиксируется, смена типа падает на сборке
  • groups и access — модель private внутри группы, public наружу; основа dbt-mesh
  • versions — две версии витрины одновременно, пока потребители переезжают

[~2 мин] Главное: exposure — это способ сказать графу про то, что живёт вне dbt. Без него граф обрывается на последней витрине, и вопрос «кто сломается» остаётся без машинного ответа.

Разбор кода: верхний блок — объявление обученной модели как потребителя. `type: ml` (бывают ещё dashboard, notebook, application), владелец с почтой, ссылка на реестр моделей и, главное, `depends_on` — от каких моделей она зависит.

Что это даёт практически. Во-первых, exposure появляется в `dbt docs` как узел графа, и по нему видно всю цепочку от сырых таблиц до модели. Во-вторых, работают селекторы: `dbt ls --select +exposure:delivery_delay_model` покажет всё, что нужно собрать перед обучением, а `dbt build --select mart_delivery_features+` теперь честно включает и exposure.

Нижний блок — contract. `enforced: true` фиксирует схему витрины: типы и ограничения проверяются на сборке, и попытка молча поменять тип колонки падает до того, как обучение получит другие данные. Для feature mart это дешёвая страховка.

Для MLE: три строки `access` и `groups` пригодятся, когда проектов становится больше одного: модель `private` видна только внутри своей группы, `public` — снаружи. Это основа dbt-mesh, но полезно и в одном репозитории — как явная граница «сюда можно ссылаться, сюда нельзя».

Осторожно: exposure — это объявление, а не автоматика. dbt не проверяет, что модель действительно читает эту витрину; вы отвечаете за то, чтобы `depends_on` соответствовал реальности. Устаревший exposure хуже отсутствующего.

Переход: «И последнее в этом блоке — что вокруг dbt изменил AI».

Рассказ: три уровня.

dbt Copilot — встроенный ассистент dbt Cloud: генерирует модели, тесты, описания и определения метрик, опираясь на ваш проект. Полезен на рутине — описать сорок колонок руками никто не хочет.

Без него ассистент угадывает схему по обрывкам файлов; с ним — спрашивает.

dbt Wizard — агент, заточенный не под «напиши SQL», а под весь цикл аналитической инженерии: разобраться в чужом проекте, внести правку, проверить результат. [~2 мин] Главное: dbt оказался удобной средой для агента не из-за AI-функций, а из-за свойства, которое было у него всегда: у каждого действия есть машинно проверяемый результат.

Рассказ: пройти по циклу на схеме. Агент читает контекст через MCP — не гадает, а спрашивает про модели и колонки. Пишет правку. [~1.5 мин] Главное: витрина в ClickHouse закрывает offline-часть feature store и не закрывает online-часть.

Рассказ: сказать прямо: для очень многих задач offline-части достаточно. Батч-скоринг раз в сутки, еженедельный пересчёт рекомендаций, аналитические ML-задачи — там online-хранилище не нужно вовсе, и заводить Feast ради галочки не стоит.

Online-хранилище нужно, когда признак требуется по ключу за миллисекунды в момент запроса пользователя.

Для MLE: ключевой риск при переходе к online — online/offline consistency. Тот же признак, посчитанный двумя разными путями, почти гарантированно разойдётся. Это и есть training/serving skew, только теперь на уровне инфраструктуры.

Пример: если Olist-модель отвечает на вопрос «успеет ли заказ» прямо в момент оформления, `seller_avg_delay_90d` нужен за миллисекунды — и тогда нужен online-слой. Если прогноз считается ночью для всех вчерашних заказов — не нужен.

Осторожно: не говорить, что «dbt заменяет feature store». Он закрывает часть задач, и честнее это назвать явно.

Training/serving skew: три источника расхождения

 ИСТОЧНИК            КАК ВЫГЛЯДИТ                     ЧЕМ ЛЕЧИТСЯ
 ────────────────    ─────────────────────────────    ───────────────────────
 разный код          train: SQL в витрине             один слой признаков,
                     serve: pandas в сервисе          общий для обеих сторон

 разные данные       train: вся история завершена     time-based split,
                     serve: половина «в пути»         фильтр по факту

 разное время        train: avg по всему окну         верхняя грань по
                     serve: avg по прошлому           моменту предсказания

 ────────────────────────────────────────────────────────────────────────────
 СИМПТОМ:  метрика на валидации хорошая, в проде хуже — и разрыв не сокращается
 ПРОВЕРКА: посчитать признак обоими путями на одних и тех же ключах и сравнить

Skew — это не одна проблема, а три разные, и лечатся они по-разному. Спутать их легко, потому что симптом у всех один: на валидации хорошо, в проде хуже.

Разный код. Самый частый и самый простой. Признак посчитан в витрине одним SQL, а в сервисе инференса — другим кодом, написанным другим человеком через полгода. Формулы совпадают процентов на девяносто, и вот эти десять процентов и есть разрыв. Лечится ровно тем, о чём была лекция: один версионируемый слой признаков, который кормит обе стороны.

Разные данные. Обучающая выборка собрана по завершённым событиям — все заказы доставлены, все исходы известны. В проде половина заказов ещё «в пути», и распределение входа другое. Лечится честным разделением по времени и явным решением, что делать со строками, где исход неизвестен (в Olist это `is_late_delivery is null`).

Разное время. Самый коварный: агрегат в обучении посчитан по окну «вокруг» события, а в проде — только по прошлому. Это и есть point-in-time из основной части.

Практическая проверка, которую стоит завести один раз и держать: взять сотню ключей, посчитать по ним признаки обоими путями — витриной и продовым кодом — и сравнить. Расхождение больше нуля значит, что один из трёх источников у вас активен. Это дешёвый регрессионный тест, который ловит целый класс проблем до того, как их увидит метрика.

Point-in-time — самая известная утечка, но не единственная. Полезно держать этот список как чек-лист перед тем, как поверить хорошей метрике.

Temporal leakage мы разобрали в основной части: признак несёт информацию из будущего.

Target leakage — прямее и обиднее. В витрину попала колонка, из которой таргет выводится напрямую. В Olist это `order_delivered_customer_date`: она в той же строке заказа, и если не выкинуть её из признаков, модель просто прочитает ответ. Симптом узнаваемый — ROC AUC около единицы.

Group leakage — про разбиение. Если заказы одного продавца попали и в train, и в valid, модель запомнила продавца, а не выучила закономерность. Для Olist разбивать надо по `seller_id` или по времени, а не случайно по строкам.

Preprocessing leakage — классика: среднее и стандартное отклонение для нормализации посчитаны по всей выборке, включая валидацию. Формально данные не смешаны, а информация уже перетекла.

Duplicate leakage — то, о чём был слайд про ClickHouse. `ReplacingMergeTree` схлопывает дубликаты в фоне; прочитали таблицу до схлопывания и без `FINAL` — часть строк попала в выборку дважды и получила двойной вес.

Общее свойство всех пяти: ни одна не ловится обычными тестами качества данных. `not_null` и `unique` на такой витрине зелёные. Ловятся они ревью, бэктестом и здоровым подозрением к слишком хорошей метрике.

Feature store: когда он действительно нужен

  • Нужен, когда признак требуется по ключу за единицы миллисекунд в момент запроса
  • Нужен, когда одни и те же признаки переиспользуют несколько команд и моделей
  • Нужен, когда online- и offline-расчёт обязаны совпадать по определению
  • НЕ нужен для батч-скоринга раз в сутки — витрины в хранилище достаточно
  • НЕ нужен, когда модель одна и признаки использует только она
  • Цена: ещё одна система в проде, ещё один источник рассинхрона

Витрина в ClickHouse закрывает offline-часть feature store и не закрывает online-часть. Для очень многих задач этого достаточно, и заводить Feast ради галочки не стоит.

Когда достаточно витрины. Батч-скоринг раз в сутки, еженедельный пересчёт рекомендаций, аналитические ML-задачи, одна модель на команду. Здесь online-хранилище не нужно вовсе, а вся ценность feature store — переиспользование, версии, владельцы — уже получена из dbt: git, `meta.owner`, описания, тесты.

Когда нужен. Пять вопросов слева — практический фильтр. Если хоть на один ответ «да», разговор про отдельный слой становится осмысленным. Главный из них первый: признак нужен по ключу за миллисекунды в момент запроса пользователя. Второй по важности — переиспользование между командами: как только один и тот же признак считают в трёх местах, реестр перестаёт быть роскошью.

Ключевой риск при переходе — online/offline consistency. Тот же признак, посчитанный двумя разными путями, почти гарантированно разойдётся. Это тот самый training/serving skew, только теперь на уровне инфраструктуры, и feature store решает его не сам по себе, а если его правильно встроить: одно определение признака, две материализации.

Пример на Olist. Если модель отвечает на вопрос «успеет ли заказ» прямо в момент оформления, `seller_avg_delay_90d` нужен за миллисекунды — тогда нужен online-слой. Если прогноз считается ночью для всех вчерашних заказов — не нужен.

Не говорите, что «dbt заменяет feature store». Он закрывает часть задач, и честнее это назвать явно.

Инструмент не влияет на результат — на выходе всё равно SQL в git, — но сильно влияет на скорость правок. Голый CLI честен и переносим, однако редактор не знает про ваши модели: нет автодополнения `ref`, нет подсказки по колонкам, ошибка находится только при запуске.

Макросы в проекте: диспетчеризация и границы

  • Макросы живут в macros/ и доступны всему проекту без импортов
  • adapter.dispatch выбирает реализацию по адаптеру: default__ и clickhouse__
  • Так один и тот же проект компилируется под несколько СУБД
  • Макросы описываются в YAML наравне с моделями — иначе их никто не найдёт
  • Граница простая: макрос ради двух строк вредит читаемости больше, чем помогает
macros/date_diff.sql — один вызов, разные СУБД
{% macro date_diff_days(a, b) %}
  {{ return(adapter.dispatch('date_diff_days')(a, b)) }}
{% endmacro %}

{% macro default__date_diff_days(a, b) %}
  datediff('day', {{ a }}, {{ b }})
{% endmacro %}

{% macro clickhouse__date_diff_days(a, b) %}
  dateDiff('day', {{ a }}, {{ b }})
{% endmacro %}
📚 Материалы: adapter.dispatch

Три вещи, которые отличают проектные макросы от случайных вставок. Первое — место: каталог `macros/`, откуда они видны всему проекту без импортов; пакеты (`dbt_utils.star`) вызываются с префиксом, и префикс здесь полезен — по нему видно, чей код исполняется.

Второе — диспетчеризация. `adapter.dispatch` выбирает реализацию по текущему адаптеру: `default` работает везде, `clickhouse` подменяет её на ClickHouse. Это тот самый механизм, которым пакеты добиваются переносимости, и он же нужен вам, если проект компилируется под несколько хранилищ. Ровно его требует настроить `dbt_project_evaluator` — блок `dispatch`, который мы видели на слайде про него.

Третье — описание. Макрос без документации в YAML не найдёт никто, включая вас через полгода; он просто будет написан заново рядом. И честная граница: макрос оправдан, когда логика повторяется и меняется вместе. Если это две строки в одном месте — оставьте SQL: скомпилированный текст читать проще, чем цепочку из четырёх макросов, каждый из которых вызывает следующий.

Data Vault и AutomateDV

  • Hub — бизнес-ключ, Link — связь между ключами, Satellite — атрибуты и их история
  • Новый источник добавляется рядом, а не переписывает существующие таблицы
  • AutomateDV собирает SQL по метаданным, staging считает хеш-ключи и hashdiff
  • Satellite обычно incremental: история пишется вставками, без обновлений
  • Цена подхода — много таблиц и обязательный слой витрин поверх для BI

{{ config(materialized='incremental') }}

{{ automate_dv.hub(

-- SQL хаба генерируется по метаданным,
-- руками он не пишется
📚 Материалы: AutomateDV

Data Vault решает конкретную боль: источников много, они меняются, а переделывать схему каждый раз дорого. Модель раскладывается на три вида таблиц — Hub (бизнес-ключ), Link (связь) и Satellite (атрибуты с историей). Ключевое свойство: новый источник добавляется рядом новой сателлит-таблицей, а существующие не переписываются, и грузиться всё это может параллельно.

Руками такой SQL никто не пишет. AutomateDV (бывший dbtVault) генерирует его по метаданным: в staging-слое считаются хеш-ключи и `hashdiff`, а модель хаба или сателлита — это вызов макроса с описанием полей. Сателлиты обычно `incremental`, потому что история пишется вставками, а не обновлениями.

Честно про цену. Таблиц становится в разы больше, читать их напрямую невозможно, поэтому поверх обязательно нужен слой витрин (тот самый Kimball с фактами и измерениями) — иначе BI просто не поедет. Поэтому Data Vault оправдан там, где источников много и они живут своей жизнью; для одного продуктового источника это оверинжиниринг.

Права доступа: что делает dbt, а что DBA

  • grants — структурированный конфиг: dbt выдаёт права сам после сборки модели
  • Плюс перед привилегией добавляет получателей, без плюса — заменяет список
  • На sources, схемы и сам кластер прав dbt не выдаёт — это остаётся за DBA
  • Роли разделяем: dev пишет в свою схему, прод-роль ходит только в прод
  • Пароли и ключи — через env_var в profiles.yml, а не строкой в репозитории
dbt_project.yml — гранты как конфиг, а не post-hook
models:
  my_project:
    marts:
      +grants:
        select: ['analyst', 'bi_service']

# без плюса — список заменяет существующий
# с плюсом (+select) — добавляет к нему
# применяется после сборки каждой модели
📚 Материалы: grants

До версии 1.2 права раздавали `post-hook` с самописным `GRANT`. Теперь есть конфиг `grants`: вы объявляете, кому что можно, а dbt сам применяет права после сборки модели — на нужном диалекте и без ручного SQL. Работает на моделях, seed-ах и снапшотах, объявляется в `dbt_project.yml`, в YAML-свойствах или прямо в модели.

Одна деталь ломает больше всего сборок: плюс перед привилегией. `select:` — заменить список получателей целиком, `+select:` — добавить к унаследованному. Перепутали — и вы молча отобрали доступ у половины BI.

Важнее понять границу. dbt управляет правами только на то, что создал сам. Доступ к сырым источникам, права на схемы, роли и пользователи в ClickHouse или Snowflake — это по-прежнему работа DBA, и dbt туда не лезет. Практическое правило: у разработчика своя схема и своя роль, у прода — отдельная, с записью только в прод. А пароли и ключи в `profiles.yml` подставляются через `env_var`: профиль в репозитории должен быть безопасен для чтения любым, у кого есть доступ к коду.

Пакеты: версии, обновление и риски

  • Версия пинится диапазоном или тегом — «последняя» ломает сборку в чужой день
  • package-lock.yml коммитим, каталог dbt_packages/ — нет
  • Пакет — это чужой код в вашем проекте, его макросы могут переопределить ваши
  • Транзитивные зависимости конфликтуют по версиям, dbt deps скажет об этом сразу
  • Обновление пакета — отдельный MR с прогоном тестов, а не «заодно с фичей»
packages.yml — версии пинятся, dbt_packages не коммитим
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.3.0", "<2.0.0"]

  - package: calogica/dbt_expectations
    version: 0.10.4

  - git: https://github.com/org/dbt-internal.git
    revision: v1.2.0      # тег, а не ветка

# dbt deps  -> dbt_packages/  (в .gitignore)
# package-lock.yml коммитим: он фиксирует,
# что реально скачалось
📚 Материалы: packages.yml · dbt deps

Пакеты — это зависимости, и обращаться с ними надо как с зависимостями кода. Версию всегда пиньте: диапазоном (`>=1.3.0, <2.0.0`) или точным значением; для приватных пакетов из git указывайте тег, а не ветку, иначе сборка меняется в тот день, когда кто-то запушил в main чужого репозитория. С dbt 1.7 рядом появляется `package-lock.yml` — его коммитят, потому что он фиксирует то, что скачалось на самом деле, а сам каталог `dbt_packages/` в git не хранят: он воспроизводится командой `dbt deps`.

Риск, о котором забывают: макросы пакета живут в одном пространстве имён с вашими. Пакет может переопределить макрос, а два пакета — потребовать несовместимые версии третьего; `dbt deps` сообщает о конфликте, но выбор остаётся за вами. Поэтому вызов через префикс (`dbt_utils.star`) — не формальность, а способ понимать, чей код исполняется.

И организационное правило: обновление пакета — это отдельный merge request с прогоном тестов и чтением changelog. В major-версиях пакеты меняют сигнатуры макросов, и такая правка, приехавшая «заодно» с продуктовой фичей, превращает разбор падения в археологию.

Пакеты в CI и проде: воспроизводимость

  • dbt deps — шаг пайплайна, а не то, что каждый делает у себя руками
  • Кэш dbt_packages экономит минуты, package-lock.yml гарантирует те же версии
  • Приватный пакет тянут по git+тегу с токеном из переменной CI, не из URL в репозитории
  • В docker-образ для прода пакеты кладут на этапе сборки, а не в рантайме
  • Обновление пакетов — отдельный MR со своим прогоном, а не сюрприз в ночном ране

Пакеты ломают сборку не в разработке, а в CI и проде — потому что там никто не помнит, что нужно выполнить `dbt deps`. Правило простое: deps — это шаг пайплайна. Рядом стоят две оптимизации: кэш каталога `dbt_packages` (минуты на каждом прогоне) и `package-lock.yml`, который гарантирует, что в CI и на ноутбуке приехало одно и то же.

Приватные пакеты — отдельная тема безопасности. В `packages.yml` хранится только ссылка и тег; токен приезжает переменной окружения CI и никогда не коммитится в URL. Это ровно тот случай, когда «работает и так» означает утечку в истории git.

В проде порядок тот же, но жёстче: пакеты ставятся на этапе сборки образа, чтобы контейнер не ходил в интернет в рантайме, а обновление пакета оформляется отдельным merge request со своим прогоном тестов. Иначе разбор ночного падения начинается с вопроса «а что у нас вообще изменилось», на который нет ответа.

Snapshots и docs: история + смысл поля

  • Snapshot реализует SCD2: сохраняет версии бизнес-сущности во времени
  • unique_key определяет объект, а check_cols — что считать изменением
  • dbt добавляет интервалы валидности, чтобы запросить «состояние на дату»
  • Docs-блок хранит одно описание и подставляется в несколько мест
  • Документация становится частью ревьюируемого кода
snapshots/customers_scd.sql · models/_docs.sql
-- snapshot: новая версия строки при смене status
{% snapshot customers_scd %}
  {{ config(strategy='check', unique_key='id',
            check_cols=['name', 'status']) }}
  select id, name, status, updated_at
  from {{ source('raw', 'customers') }}
{% endsnapshot %}

-- docs-блок переиспользуется в schema.yml и dbt docs
{% docs stg_orders__amount %}
Сумма заказа после скидок и налогов.
{% enddocs %}

Snapshot — это механизм историзации SCD2 для случаев, когда источник хранит только актуальную строку. Здесь id определяет клиента, а изменение name или status создаёт новую версию. После запуска можно спросить: «какой статус был у клиента на конец прошлого месяца?» — и ответить без отдельной самописной таблицы истории.

Важно согласовать список check_cols: слишком широкий даёт лишние версии от технических полей, слишком узкий пропускает бизнес-изменения. Snapshots не заменяют CDC автоматически; это удобный dbt-слой, когда семантика и объём данных подходят.

Блок {% docs %} решает другую задачу — единый смысл атрибута. Его можно вставить в schema.yml и получить в dbt docs generate, поэтому описание меняется вместе с моделью в том же MR. Это особенно ценно для метрик и финансовых полей, где «сумма» без правил расчёта мало что означает.

Материализованные представления: ClickHouse

  • В ClickHouse MV — не кэш, а триггер на вставку: агрегат считается в момент INSERT
  • Приёмник обычно AggregatingMergeTree, и GROUP BY совпадает с его ORDER BY
  • catchup=True сначала догоняет историю, потом создаёт саму MV
  • Refreshable MV пересчитывает всё по расписанию — можно JOIN, но свежесть ниже
  • В dbt это materialized_view: одна модель описывает и MV, и таблицу-приёмник
models/marts/mv_visits_daily.sql
{{ config(
    materialized='materialized_view',
    engine='AggregatingMergeTree()',
    order_by='(day, country)',
    catchup=True) }}

select toDate(ts) as day, country,
       countState()       as visits,
       uniqState(user_id) as users
from {{ source('raw', 'events') }}
group by day, country
📚 Материалы: dbt-clickhouse MV · Incremental MV

Главное недоразумение: в ClickHouse материализованное представление — это не кэш запроса, а триггер на вставку. Данные приезжают в исходную таблицу, MV в этот момент считает свою часть агрегата и кладёт результат в таблицу-приёмник. Читаете вы приёмник, и он всегда актуален по мере вставок.

Отсюда два правила. Приёмник берут AggregatingMergeTree (или SummingMergeTree), а состояния пишут через `-State`-функции — `countState`, `uniqState`; при чтении их сворачивают `-Merge`. И `GROUP BY` в MV должен совпадать с `ORDER BY` приёмника, иначе строки не схлопнутся и таблица распухнет.

В dbt это отдельная материализация `materialized_view` адаптера ClickHouse: одна модель описывает и представление, и приёмник, а `catchup=True` догоняет историю перед созданием. Отдельно стоят refreshable MV — они периодически пересчитывают весь результат, поэтому поддерживают JOIN-ы. Выбор простой: инкрементальная MV — когда нужна свежесть на вставке; refreshable — когда нужны сложные соединения и можно потерпеть задержку.

Микробатчинг: инкремент окнами времени

  • Одна большая дельта разбивается на независимые окна по времени
  • batch_size — hour, day (по умолчанию), month или year
  • lookback пересчитывает несколько прошлых окон — для опоздавших событий
  • Упал один батч — перезапускается он, а не весь бэкфилл
  • dbt сам фильтрует upstream-модели, у которых объявлен event_time
models/marts/fct_orders.sql
{{ config(
    materialized='incremental',
    incremental_strategy='microbatch',
    event_time='order_date',
    batch_size='day',
    lookback=3,
    begin='2026-01-01') }}

select * from {{ ref('stg_orders') }}
-- фильтр по окну dbt подставит сам:
-- is_incremental() здесь не нужен
📚 Материалы: microbatch

Обычная инкрементальная модель делает один большой запрос на всю дельту. Пока данных мало — нормально; на бэкфилле за год это один запрос на миллиарды строк, который падает по памяти на девяносто восьмом проценте и начинается сначала.

Стратегия microbatch (dbt 1.9) переворачивает это: модель объявляет `event_time`, `batch_size` и начало истории, а dbt сам режет период на окна и выполняет по запросу на окно. Предикат подставляется автоматически — писать `is_incremental()` и вручную считать `max(order_date)` больше не нужно.

Два следствия, ради которых всё затевалось. Первое: упавший батч перезапускается отдельно, остальные остаются на месте. Второе: `lookback` заставляет пересчитывать несколько прошлых окон, что закрывает вечную проблему опоздавших событий. Плюс dbt автоматически подрезает upstream-модели, у которых тоже объявлен event_time, — граф перестаёт читать лишнее.

dbt и потоковые данные: где проходит граница

  • dbt описывает SQL-преобразование; непрерывность обеспечивает движок, а не dbt run
  • RisingWave: materialized_view вместо incremental, отдельная материализация sink
  • Потоковая MV пересчитывается сама — запрос всегда видит свежий результат
  • В Spark и Databricks роль такой модели играют streaming tables поверх Structured Streaming
  • Задача dbt здесь — версии, тесты и доки для потоковых определений

       count(*) as orders

            order_ts,
            interval '1 minute')
group by window_start

-- обновляется само, dbt run не нужен
📚 Материалы: dbt-risingwave

Вопрос «умеет ли dbt в стриминг» поставлен неточно. dbt — это генератор SQL и оркестратор графа, у него нет собственного рантайма; непрерывность даёт движок под ним, а dbt описывает, что именно считать.

Практически это выглядит так. В RisingWave модель материализуется как `materialized_view` — потоковая MV, которая обновляется сама по мере прихода событий; `incremental` там просто не нужен, а для выгрузки наружу есть материализация `sink`. В экосистеме Spark ту же роль играют streaming tables поверх Structured Streaming. В обоих случаях `dbt run` — это деплой определения, а не запуск обработки каждую минуту.

Что остаётся за dbt и ради чего его сюда тащат: потоковые определения попадают в git, получают тесты, описания и lineage наравне с батчевыми моделями. Граница проходит по свежести: секунды — стриминговый движок, минуты и часы — микробатчинг из предыдущего слайда, и это дешевле в эксплуатации.

Semantic Layer / MetricFlow

  • Единое определение метрик — один раз, в коде
  • MetricFlow генерирует корректный SQL по запросу метрики
  • Убирает расхождения метрик между дашбордами
  • Метрики доступны из BI, ноутбуков и через API
  • Консистентность и переиспользование бизнес-логики
📚 Материалы: About MetricFlow · MetricFlow commands

Больная тема любой аналитики — когда «выручка» в двух дашбордах считается по-разному. Semantic Layer решает это: метрика определяется один раз в коде, а не переписывается в каждом BI-инструменте.

Движок MetricFlow сам генерирует корректный SQL под каждый запрос. Метрики доступны из BI, ноутбуков и по API — и везде считаются одинаково. Это особенно важно, когда одна и та же метрика используется в отчётах, алертах и data products.

Практический смысл для команды — одна формула, один владелец, один контур тестирования. Консистентность и переиспользование бизнес-логики.

Jinja: SWOT шаблонного подхода

📚 Материалы: Jinja в dbt

Соберём разговор про Jinja в один честный SWOT. Сильная сторона и слабая — это одно и то же свойство, посмотренное с разных сторон: Jinja ничего не знает о SQL. Именно поэтому он работает с любым диалектом и любым движком, и именно поэтому он не может подсказать вам ни колонку, ни тип, ни то, что вы разорвали выражение пополам.

Возможности — там, где логика повторяется и описывается метаданными: пивот по значениям из данных, генерация staging через codegen, хабы и сателлиты AutomateDV, единый проект под несколько СУБД. Всё это без шаблонов пришлось бы писать руками или внешним генератором.

Угрозы начинаются, когда шаблонов становится больше, чем SQL. Проект превращается в программу, которая печатает SQL: отладка идёт через `target/compiled`, а не через чтение модели, и цена каждого следующего макроса растёт. Второй, более медленный риск — направление индустрии: чтобы строить lineage на уровне колонок, движку нужно разбирать SQL, а не склеивать строки. Об этом следующий слайд.

Почему другие движки уходят от шаблонов

  • SQLMesh: макросы правят семантическое представление запроса (SQLGlot), а не текст
  • В его документации претензия прямая — шаблонизатор намеренно ничего не знает о языке, который шаблонизирует
  • Spark SDP: датасеты объявлены кодом (.py или .sql), таблицы в цикле — обычный Python, шаблонного слоя нет
  • Bruin — контрпример: он как раз на Jinja, со своими start_date/end_date, циклами и условиями
  • Уходят не «все», а те, кто строит lineage по колонкам: для этого SQL надо разбирать
одно ограничение — текстом и над разобранным SQL
-- dbt + Jinja: подстановка текста
{% set cutoff = var('cutoff_days', 30) %}
select * from {{ ref('orders') }}
where order_date >= current_date - {{ cutoff }}

-- SQLMesh: макрос над разобранным SQL
@DEF(cutoff, 30);
SELECT * FROM orders
WHERE order_date >= CURRENT_DATE - @cutoff;
📚 Материалы: SQLMesh macros · Spark Declarative Pipelines

Сначала поправка к расхожему тезису: «все уходят от Jinja» — миф. Bruin, один из самых заметных новых инструментов, построен ровно на нём: переменные `start_date` и `end_date`, циклы, условия — знакомая картина. Уходят не все, а те, кому мешает конкретное свойство.

Свойство это — слепота к SQL. У SQLMesh макросы правят семантическое представление запроса, разобранное библиотекой SQLGlot, и поэтому движок сам понимает, подставить ли строковый литерал или идентификатор. В документации претензия сформулирована прямо: шаблонизатор намеренно ничего не знает о языке, который шаблонизирует. Показательно, что Jinja там при этом поддержан — его не запрещают, его понижают в статусе.

Spark Declarative Pipelines решают задачу иначе: там нет шаблонного слоя вовсе. Исходники — `.py` или `.sql`, датасеты объявляются кодом через `pyspark.pipelines`, и если нужно создать двадцать похожих таблиц, это обычный питоновский цикл, а не текст с дырками.

Общий знаменатель — column-level lineage и анализ влияния. Чтобы сказать «эта правка ломает вот эту колонку в вон той витрине», движок обязан разобрать SQL. И то же самое сейчас делает сам dbt: Fusion разбирает SQL и вводит строгую спецификацию языка — та же критика, пришедшая изнутри.

Раньше на этом месте было три слайда сравнения — сведём их в один честный SWOT. Сильные стороны SQLMesh технические и реальные: он разбирает SQL в синтаксическое дерево через SQLGlot, поэтому знает lineage на уровне колонок и отличает ломающее изменение от безобидного. Виртуальные среды делают «свою копию хранилища на ветку» дешёвой, а `plan` показывает влияние правки до применения.

Слабости — не в технике, а вокруг неё: пакетов меньше, статей и курсов меньше, нанимать сложнее, интеграции менее обкатаны. Именно это чаще всего и решает исход спора в команде.

Возможности — там, где нет груза legacy: новый проект, дорогие preview-среды, желание получить impact analysis. Причём переходить целиком не обязательно: SQLMesh умеет запускаться поверх существующего dbt-проекта (следующий слайд). Угрозы — миграция ради миграции, двойной стек, когда половина команды живёт в одном инструменте, а половина в другом, и зависимость от одного вендора. Практический вывод курса: на greenfield SQLMesh стоит рассматривать всерьёз, а работающий dbt-проект переносят только под конкретную боль, которую можно назвать вслух.

SQLMesh поверх существующего dbt-проекта

  • Проект не переписывается: init читает dbt_project.yml и profiles.yml
  • Модели, seeds и пакеты (dbt deps) остаются на месте
  • dbt-тесты становятся audits; sqlmesh test — это юнит-тесты запросов
  • is_incremental() меняется на sqlmesh_incremental и временные переменные
  • Поддержано не всё: часть jinja-методов и отдельные настройки snapshots

Это ответ на главное возражение «у нас уже сто моделей на dbt». SQLMesh умеет работать как движок поверх вашего dbt-проекта: `sqlmesh init -t dbt` из корня проекта читает `dbt_project.yml` и `profiles.yml`, забирает модели, seeds и подключения. Переписывать SQL не нужно — модели остаются dbt-моделями с `ref()` и Jinja, а рядом появляется `sqlmesh.yaml` со своими настройками по умолчанию.

Что меняется в терминах. dbt-тесты приезжают как audits; при этом слово `test` в SQLMesh занято под юнит-тесты логики запроса — это разные вещи, и путаница здесь стоит дорого. Окружения SQLMesh создаёт сам во время `plan`, поэтому хардкодить target в профиле не нужно: профиль указывает на прод, остальное берёт на себя движок.

Честные ограничения тоже стоит назвать. Инкрементальные блоки `is_incremental()` заменяются на sqlmesh_incremental с предопределёнными временными переменными; часть jinja-методов (`debug`, обход `graph.nodes`) недоступна; у snapshots не поддержан `invalidate_hard_deletes=False`; типы seed-колонок иногда приходится указывать явно. Поэтому реалистичный сценарий — не «переезд в пятницу», а параллельный запуск на копии проекта: увидеть plan, оценить impact analysis и уже потом решать.

Декларативные трансформации: ещё четыре подхода

  • Bruin — один CLI для ingestion, SQL/Python assets, quality checks и lineage в repo
  • Spark Declarative Pipelines (SDP) — SQL/Python для batch и streaming-графов
  • Databricks Lakeflow — managed-пайплайны: flows, streaming tables, materialized views
  • Snowflake Dynamic Tables — SELECT + TARGET_LAG; платформа сама ведёт refresh и порядок DAG
  • Выбор: portable dbt/SQLMesh/Bruin или нативные возможности конкретной платформы
📚 Материалы: Bruin overview · Spark Declarative Pipelines · Lakeflow pipelines · Snowflake Dynamic Tables guide

Тренд шире одного dbt: команды всё чаще описывают желаемый набор данных и зависимости, а не последовательность низкоуровневых задач. Bruin объединяет ingestion, SQL/Python-преобразования, quality checks и lineage в репозитории — полезно, когда хочется меньше разрозненных инструментов.

В Spark-экосистеме Spark Declarative Pipelines описывает batch и streaming-пайплайны в SQL или Python. Databricks Lakeflow — управляемая реализация этого подхода: платформа анализирует зависимости и оркестрирует flows, streaming tables и materialized views. Это естественно для Delta/streaming-нагрузок, но сильнее привязывает решение к платформе.

В Snowflake Dynamic Tables позволяют определить результат SQL-запросом и TARGET_LAG; Snowflake сам поддерживает порядок refresh и, где возможно, incremental processing. Для процедурной логики, точного cron или сложного MERGE остаются streams/tasks. dbt выигрывает переносимостью и экосистемой, нативные средства — меньшим количеством операционного кода внутри своей платформы. Современный стек часто сочетает эти подходы, а не выбирает ровно один.

КАРТИНКИ

Не входит в хронометраж лекции. Склад иллюстраций: сюда сложено то, что собрано для деки, но не встало ни на один содержательный слайд — на слайдах-кандидатах панель кода занимает всю высоту, и картинка либо не помещается, либо выдавливает текст.

Зачем это в деке, а не в папке: картинка, лежащая рядом со слайдами, переезжает на слайд одним движением в PowerPoint, а лежащая в каталоге — не переезжает никогда.

Здесь же продублированы жёлтые 🔍-ссылки на поиск картинок с тех слайдов, где иллюстрации пока нет: собранные в одном месте, они читаются как список задач, а не как разбросанные по деке пометки.

Учёт того, какая картинка где стоит, ведётся в `content/preza-dbt-v4-images.yml`; там же помечается картинка, удалённая или перенесённая вручную, — генератор такую обратно не поставит.
