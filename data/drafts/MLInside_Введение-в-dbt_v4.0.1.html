dbt: восемь инженерных свойств слоя трансформаций

  • Version control — SQL-модель лежит в git, как и код обучения
  • Modularity — модель ссылается на модель, а не копирует её текст
  • Testing — данные проверяются контрактом до того, как их увидит модель
  • Documentation — определение признака, владелец, семантика поля
  • Lineage — виден граф: от source до training dataset
  • Incremental — не пересчитываем всю историю признаков
  • CI — изменение SQL проходит ревью и автотесты
  • Orchestration — сборка встраивается в общий production-пайплайн

[~3 мин] Главное: каждая «фича dbt» — это ответ на конкретный вопрос MLOps. Если студент унесёт из лекции один слайд, пусть это будет этот.

Рассказ: идти по строкам медленно, на каждой давать один вопрос из практики.

`source()` — «откуда взялась эта колонка?». Объявленный источник даёт ответ в коде, а не в переписке.

`ref()` — «что сломается, если я изменю stg_orders?». Граф отвечает за секунды: `dbt build --select stg_orders+`.

`test` — «можно ли учиться на этой таблице сегодня?». Тест — это предусловие обучения, а не отчёт о качестве.

`docs` — «что означает delivery_delay_days и кто владелец?». Определение лежит рядом с кодом и не расходится с ним.

`incremental` — «сколько стоит обновить признаки за вчера?». Разница между полным сканом истории и одним днём — это ваш счёт за compute.

`CI` — «кто проверил, что новый признак не сломал витрину?». Ревью SQL становится обязательным, как ревью Python.

`orchestrator` — «когда можно запускать обучение?». Ответ: когда dbt build прошёл вместе с тестами, и никак иначе.

Что такое dbt: компиляция, ref() и DAG

staging: чистка и производные поля

  • Один источник — одна staging-модель, без соединений
  • Здесь появляются типы, флаги и части даты
  • Доставленным считаем по НАЛИЧИЮ даты, а не по статусу
  • NULL там, где «неизвестно» — не подменяем нулём
models/staging/stg_orders.sql
{{ config(materialized='view') }}

select
  order_id,
  customer_id,
  order_status,
  order_purchase_timestamp,
  order_delivered_customer_date,
  order_estimated_delivery_date,

  toHour(order_purchase_timestamp) as order_hour,
  toDayOfWeek(order_purchase_timestamp) as order_dow,

  -- «неизвестно» ≠ «вовремя»
  case
    when order_delivered_customer_date is null
      then null
    when dateDiff('day',
           order_estimated_delivery_date,
           order_delivered_customer_date) > 0
      then 1
    else 0
  end as is_late_delivery

from {{ source('olist_raw', 'orders') }}

[~1 мин] Главное: staging — это место, где сырые данные становятся пригодными к употреблению, и единственное место, где это делается.

Разбор кода: показать две вещи. Первая — `toHour`/`toDayOfWeek`: временные признаки считаются один раз здесь, а не в каждой витрине. Вторая — блок `case` с `null`: у 2 965 заказов Olist нет даты доставки, и мы честно ставим NULL.

Не разбирать: перечисление колонок сверху.

Для MLE: это ваш таргет. `is_late_delivery` = 1, если приехало позже обещанного. NULL означает «исход неизвестен» — такие строки из обучающей выборки надо исключать явно, а не молча считать их «вовремя».

Пример: два заказа в Olist имеют `order_status = 'delivered'` без даты доставки. Если определять доставленность по статусу, они попадут в выборку с непонятным таргетом.

Осторожно: подмена NULL нулём — самая частая тихая ошибка на этом слое. Доля просрочек сразу занижается, и модель учится не тому.

Переход: «Дальше — соединения. Это следующий слой».

intermediate: заказ ровно одной строкой

  • Позиции сворачиваем ДО соединения — иначе join размножит строки
  • Все соединения LEFT — 775 заказов не имеют позиций
  • Гранулярность названа в имени модели и проверена тестом
models/intermediate/int_order_level.sql
{{ config(materialized='table') }}

with items as (
  -- сначала свернули до заказа,
  -- только потом соединяем
  select
    order_id,
    count(*)                  as item_count,
    count(distinct seller_id) as seller_count,
    sum(price)                as items_value,
    sum(freight_value)        as freight_value
  from {{ ref('stg_order_items') }}
  group by order_id
)

select
  o.*,
  coalesce(i.item_count, 0)    as item_count,
  coalesce(i.seller_count, 0)  as seller_count,
  coalesce(i.items_value, 0)   as items_value,
  coalesce(i.freight_value, 0) as freight_value,
  d.customer_seller_distance_km
from {{ ref('stg_orders') }} as o
left join items as i using (order_id)
left join {{ ref('int_order_distance') }} as d
       using (order_id)

[~1.5 мин] Главное: одна строка = один заказ. Это утверждение, за которое модель отвечает и которое проверяется тестом.

Разбор кода: показать CTE `items` и сказать вслух: свёртка до соединения. Если сначала сджойнить позиции, а потом группировать — заказ из пяти позиций даст пять строк, и любая метрика «по заказам» поедет.

Вторая точка — `left join`. Не `inner`. 775 заказов Olist не имеют ни одной позиции; inner тихо выбросил бы их и занизил и выручку, и долю просрочек.

Не разбирать: `int_order_distance` — это отдельная модель с формулой гаверсинуса, её содержимое сейчас не важно.

Для MLE: `coalesce(..., 0)` здесь корректен: «позиций нет» действительно означает ноль позиций. Сравните со слайдом про staging, где ноль был бы ложью. Решение про NULL принимается по смыслу поля, а не по привычке.

Осторожно: «размножение строк джойном» — ошибка, которую почти невозможно заметить глазами. Ловится тестом `dbt_utils.equal_rowcount` против `stg_orders`.

Переход: «И наконец витрина признаков».

Осторожно: не класть в feature mart всё подряд «на всякий случай». Каждая колонка — это обязательство поддерживать её в проде.

sources: контракт входа и freshness

  • source — это объявление внешней таблицы, которую dbt не строит
  • Даёт lineage от сырых данных и единое место для смены схемы
  • freshness отвечает на вопрос: данные вообще доехали?
  • dbt source freshness — отдельная команда, её ставят перед сборкой

Не разбирать: `description` и полный список таблиц.

Для MLE: ставьте freshness перед сборкой признаков. Иначе типичный сценарий: ingestion молча не отработал, dbt честно пересчитал витрину по вчерашним данным, обучение прошло, метрики просели — и вы неделю ищете проблему в модели.

Пример: в Olist датасет статический, поэтому freshness там демонстрационный. В живом проекте окно ставится по SLA поставщика.

Осторожно: freshness — это проверка доехали ли данные, а не проверка их корректности. Корректность — это тесты, они дальше.

Jinja, макросы и пакеты

[~0.3 мин] Главное: блок про переиспользование.

Рассказ: «Как перестать копипастить SQL между двадцатью моделями и не превратить проект в магию».

Jinja: от копипасты к переиспользуемой платформе

  • Jinja — шаблонизатор: dbt рендерит текст модели ДО отправки в базу
  • Отсюда всё: ref(), source(), config(), is_incremental()
  • var() — параметр проекта; env_var() — значение из окружения
  • Цикл и условие позволяют не писать двадцать почти одинаковых моделей
  • Цена: SQL в редакторе больше не равен SQL в базе
models/*.sql
  (SQL + Jinja)
      │
      ↓
  dbt compile        # рендер шаблона
      │
      ↓
target/compiled/…
  (чистый SQL)
      │
      ↓
  dbt run            # + DDL, отправка в БД

[~1 мин] Главное: Jinja — это ещё один шаг сборки между вашим файлом и базой. Пока вы это помните, всё остальное просто.

Рассказ: объяснить схему в три фразы: файл модели — это шаблон; `dbt compile` превращает его в обычный SQL; в базу уезжает результат. `ref()` и `config()` — не магия dbt, а обычные функции Jinja-контекста.

Для MLE: аналогия — препроцессор или шаблон Helm. Тот же выигрыш и та же опасность: удобно, пока читаемо.

Осторожно: не рамочка «ещё одна возможность dbt». Правильная рамка — это инструмент, который позволяет одному человеку держать переиспользуемый слой трансформаций.

Переход: «Смотрим на конкретных конструкциях».

Jinja в деле: параметры, условие, цикл

  • var() — параметр с дефолтом, задаётся в dbt_project.yml или флагом
  • env_var() — секреты и адреса окружения, в git не попадают
  • target — профиль, которым запущена сборка
  • Цикл разворачивается при компиляции, база видит уже готовый SQL

[~1.5 мин] Главное: одна и та же модель по-разному собирается в dev и в проде — и это описано в коде, а не в инструкции.

Разбор кода: три строки. `var('train_window_days', 180)` — окно обучения стало параметром: поменять его можно флагом `--vars`, не трогая SQL. Рядом `env_var('CH_RAW_DB', ...)` — то же самое, но значение приходит из окружения: адрес базы и креды в git не попадают. Цикл `for st in [...]` — три почти одинаковых агрегата пишутся один раз. `if target.name == 'dev'` — в dev-профиле модель собирается на срезе, чтобы прогон занимал секунды.

Не разбирать: `{%-` и `-%}` — это управление пробелами, скажите одной фразой «минус съедает пробел» и идите дальше.

Для MLE: параметризованное окно — это ровно то, что нужно для экспериментов с признаками: собрать витрину на 90 и на 365 днях, не заводя две модели.

Пример: `dbt build --select mart_delivery_features --vars '{train_window_days: 365}'`.

Осторожно: значения `var()` идут в SQL как текст. Не подставляйте туда пользовательский ввод.

Переход: «А если один и тот же кусок логики нужен в пяти моделях — это уже макрос».

Макрос: повторяющаяся логика признака

  • Макрос возвращает фрагмент SQL, а не значение
  • Хороший кандидат — то, что уже написано дважды
  • safe_divide: деление, которое не падает и не даёт inf
macros/safe_divide.sql
{% macro safe_divide(numerator, denominator) -%}
  case
    when {{ denominator }} = 0 then null
    else {{ numerator }} / {{ denominator }}
  end
{%- endmacro %}

                 'promised_days') }} as delay_ratio
from {{ ref('int_order_level') }}

[~1.5 мин] Главное: макрос — это DRY для SQL. Не «продвинутая фича», а способ не разъехаться в определении признака.

Разбор кода: показать тело макроса — обычный `case`, обёрнутый в `{% macro %}`. Потом показать два вызова и сказать: если завтра решим, что при нулевом знаменателе нужен не NULL, а ноль — правка в одном месте.

Не разбирать: `-%}` и `{%-`.

Для MLE: доля стоимости доставки и отношение просрочки к обещанному сроку — оба признака делят одно на другое, оба ломаются на нуле. Без макроса это два разных `case`, которые через полгода будут вести себя по-разному.

Пример: та же логика нужна и в staging позиций, и в витрине по категориям. Продублируете — границы разъедутся.

Осторожно: макрос — не место для бизнес-смысла. `safe_divide` — про арифметику; «что считать просрочкой» должно остаться видимым в модели.

Переход: «Второй полезный класс макросов — ключи и окна».

Для MLE: суррогатный ключ нужен, когда гранулярность составная. В Olist пара «заказ × продавец» естественного ключа не имеет, а группировать по ней надо.

  • relationships — ссылочная целостность между слоями
  • Диапазоны и распределения — из dbt_expectations
  • dbt-тесты — это data assertions, а не constraints в БД

[~2 мин] Главное: тест — это утверждение о данных, которое проверяется на каждой сборке, а не разовая проверка при разработке.

Разбор кода: `not_null` + `unique` на `order_id` — это машинная запись фразы «одна строка на заказ». `expect_column_values_to_be_between` с `min_value: 0` — счётчик не может быть отрицательным. `relationships` — каждый заказ витрины существует в intermediate.

Не разбирать: полный список часов, он для наглядности.

Для MLE: ключевая мысль — какие колонки объявлять `not_null`. Ответ: те, что входят в контракт признака. Если модель обучения падает на пропуске в `freight_share`, значит `freight_share` обязан быть not_null, и это надо записать здесь.

Осторожно: dbt-тесты — это assertions, а не физические constraints. dbt выполняет запрос и смотрит, есть ли строки-нарушители. В базе никакого ограничения не появляется, и данные, нарушающие тест, физически лежат в таблице. Тест ловит их, а не запрещает.

Переход: «Двух видов тестов не хватает. Нужны свои проверки и проверки самой логики».

  • unit test — проверка логики модели на фикстурах, без реальных данных
  • Unit-тест ловит ошибку в SQL, а не в данных

[~2 мин] Главное: generic-тесты проверяют данные, unit-тесты проверяют ваш SQL. Это разные вопросы.

Разбор кода: верхний блок — обычный запрос. Логика dbt простая: вернул хоть одну строку — тест красный. Нижний — unit-тест: два входа, один ожидаемый выход, никаких реальных данных.

Не разбирать: где физически лежат файлы.

Для MLE: unit-тест — это ровно то, что вы делаете в pytest для функции признака, только для модели. Особенно окупается на моделях со свёрткой: «две позиции одного заказа дают item_count = 2» — правило, которое легко сломать джойном.

Пример: singular-тест из Olist: «сумма позиций заказа сходится с суммой платежей с точностью до цента». Это бизнес-правило, generic-тестами оно не выражается.

Осторожно: unit-тесты не заменяют data-тесты. Ваш SQL может быть безупречен на фикстурах и падать на реальных NULL.

Переход: «Тесты говорят, что данные целы. Документация говорит, что они значат».

Инкрементальность, ClickHouse и point-in-time

[~0.3 мин] Главное: самый ML-специфичный блок лекции.

Рассказ: «Как обновлять признаки дёшево — и как при этом не отравить обучающую выборку».

Инкремент вместо полного пересчёта

  • Full refresh: пересобираем витрину целиком, читая всю историю
  • Incremental: дописываем только новую дельту
  • is_incremental() истинно только когда таблица уже существует
  • {{ this }} — сама целевая таблица модели
  • unique_key превращает вставку в upsert изменившихся строк
models/marts/mart_delivery_features.sql
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='append') }}

select *
from {{ ref('int_order_level') }}

{% if is_incremental() %}
  -- учебный вариант: только новее
  -- максимума в самой витрине
  where order_purchase_timestamp > (
    select max(order_purchase_timestamp)
    from {{ this }}
  )
{% endif %}

[~2 мин] Главное: инкремент — это про деньги и время сборки, и именно поэтому в feature layer он почти обязателен.

Разбор кода: три точки. `materialized='incremental'` — материализация. `is_incremental()` — блок работает только при повторных прогонах; при первом запуске и при `--full-refresh` он выключен и модель собирается целиком. `{{ this }}` — ссылка на саму целевую таблицу.

Не разбирать: `incremental_strategy` — про стратегии скажем на слайде про ClickHouse.

Для MLE: посчитайте на пальцах. Витрина признаков за три года — это сотни миллионов строк и джойны. Полный пересчёт каждую ночь стоит часы compute; инкремент за сутки — минуты. Разница уходит прямо в счёт за кластер.

Пример: первый прогон Olist собирает всю историю; дальше — только новые заказы.

Осторожно: этот фильтр — учебный, а не production-паттерн. Он написан ровно так, как его пишут в первый раз, и ровно так же ломается. Почему — следующий слайд, это важно.

Переход: «Разберём, что именно здесь сломается».

Ловушка: WHERE ts > max(ts)

  • Late arrivals — событие приехало позже, чем произошло
  • Corrections — строку в источнике поправили задним числом

  • Во всех трёх случаях фильтр по максимуму данные просто не увидит
  • Хуже всего: пайплайн зелёный, тесты зелёные, витрина неверна

[~1.5 мин] Главное: `WHERE ts > max(ts)` предполагает, что данные приходят строго по возрастанию времени события. В проде это почти никогда не так.

Рассказ: три сценария. Первый — опоздание: событие произошло восьмого, а доехало одиннадцатого; максимум в витрине уже двенадцатое, и строка не попадёт никогда. Второй — исправление: заказ пятого марта переоформили, дата события не изменилась, фильтр его не поднимет. Третий — изменяемый источник: у заказа Olist статус и дата доставки дописываются позже, чем он был создан.

Подчеркнуть худшее свойство этой ошибки: она молчаливая. Тесты проверяют то, что в таблице есть; отсутствующие строки они проверить не могут.

Для MLE: для обучения это означает систематическое смещение. Опоздавшие заказы — это чаще всего именно проблемные заказы. Выбросив их, вы обучаете модель на выборке, где просрочек меньше, чем в реальности.

Осторожно: не превращать это в «инкремент — зло». Инкремент нужен; неверна конкретная стратегия отбора дельты.

Переход: «Как делать правильно».

Безопасная стратегия: watermark, lookback, идемпотентность

  • Считаем по времени ЗАГРУЗКИ или по окну, а не по максимуму факта
  • lookback — перекрываем окно назад, чтобы поднять опоздавшее
  • unique_key + delete+insert — повторный прогон не плодит дубли
  • Идемпотентность: два прогона подряд дают одинаковый результат
  • Партиции: пересобрать день целиком часто дешевле, чем искать дельту
models/marts/mart_delivery_features.sql
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='delete+insert') }}

select * from {{ ref('int_order_level') }}

{% if is_incremental() %}
  -- окно с перекрытием: сутки инкремента
  -- плюс lookback на опоздавшие и правки
  where order_purchase_timestamp >=
        (select max(order_purchase_timestamp)
         from {{ this }})
        - interval {{ var('lookback_days', 7) }} day
{% endif %}

[~2 мин] Главное: дельта считается с перекрытием, а повторная запись обязана быть безопасной.

Разбор кода: две строки. `incremental_strategy='delete+insert'` вместе с `unique_key` означает: перед вставкой строки с такими же ключами удаляются. Второй прогон на тех же данных даёт тот же результат — это и есть идемпотентность. И `- interval lookback_days day`: мы сознательно перечитываем последние семь дней, чтобы поднять опоздавшее и исправленное.

Не разбирать: как именно ClickHouse исполняет delete+insert.

Для MLE: lookback — это компромисс, который вы обязаны выбрать осознанно. Семь дней стоят в семь раз дороже одного и покрывают опоздания до недели. Ответ на вопрос «сколько» даёт не интуиция, а распределение задержки между временем события и временем загрузки в ваших данных.

Пример: ещё надёжнее — партиционирование. Витрина партиционирована по месяцу; пересобираем затронутые партиции целиком. Никакой дельта-логики, полная воспроизводимость, цена — перечитанная партиция.

Осторожно: идемпотентность надо проверять. Прогон дважды подряд и сравнение `count()` — минимальный тест, который ловит большинство ошибок инкремента.

Переход: «Теперь про специфику движка — у нас ClickHouse».

[~3 мин] Главное: правильно посчитанный SQL-агрегат может быть неверным признаком. Для ML недостаточно корректной арифметики — нужна корректность по времени.

Рассказ: разобрать пример медленно, он того стоит. Мы предсказываем просрочку заказа X, оформленного первого марта в десять утра. Один из признаков — средняя просрочка этого продавца.

Наивный SQL: `avg(delivery_delay_days) group by seller_id`. Он посчитает среднее по всем заказам продавца, которые есть в таблице, — включая заказы C и D, которые завершились после первого марта. В момент предсказания этой информации не существовало.

Модель на такой выборке покажет отличные метрики на валидации и просядет в проде. Классическая утечка: признак несёт информацию из будущего.

Для MLE: правило формулируется одной строкой и должно висеть у вас перед глазами: feature_timestamp <= prediction_timestamp. Любой агрегат по истории обязан быть ограничен сверху моментом предсказания.

Пример: в Olist это особенно коварно, потому что `order_delivered_customer_date` дописывается в ту же строку заказа позже. Таблица выглядит так, будто всё было известно сразу.

Осторожно: утечка не ловится обычными dbt-тестами. `not_null` и `unique` на такой витрине зелёные. Ловится она либо ревью SQL, либо аномально высокой метрикой на валидации — и второе замечают не все.

Переход: «Смотрим, как это выражается в SQL».

Point-in-time на SQL: история продавца как было

models/intermediate/int_seller_delay_history.sql
{{ config(materialized='table') }}

with order_seller as (                    -- продавец заказа
  select order_id, min(seller_id) as seller_id
  from {{ ref('stg_order_items') }} group by order_id
),
history as (                              -- ЗАВЕРШЁННЫЕ заказы продавцов
  select os.seller_id,
         o.order_delivered_customer_date                  as done_at,
         dateDiff('day', o.order_estimated_delivery_date,
                         o.order_delivered_customer_date) as delay_days
  from {{ ref('stg_orders') }} as o
  join order_seller as os using (order_id)
  where o.order_delivered_customer_date is not null
)
select
  cur.order_id,
  avg(h.delay_days) as seller_avg_delay_90d,
  count(h.done_at)  as seller_orders_90d
from {{ ref('stg_orders') }} as cur
join order_seller as cs using (order_id)
left join history as h on h.seller_id = cs.seller_id
      -- ВОТ ЭТИ ДВЕ СТРОКИ И ЕСТЬ POINT-IN-TIME
      and h.done_at <  cur.order_purchase_timestamp
      and h.done_at >= cur.order_purchase_timestamp - interval 90 day
group by cur.order_id

[~2 мин] Главное: point-in-time — это два условия в JOIN, а не отдельная технология.

Разбор кода: показать ровно две строки, помеченные комментарием. Верхняя — строго раньше момента покупки: берём только то, что было известно. Нижняя — окно 90 дней назад: не тащим всю историю, признак должен быть про недавнее поведение.

Обратить внимание: ключевое условие стоит на дате завершения (`done_at`) исторического заказа, а не на дате его покупки. Заказ, купленный в феврале и доставленный в апреле, на первое марта ещё не был завершён — и в среднее входить не должен.

Не разбирать: CTE `order_seller` (у заказа может быть несколько продавцов, берём одного) и производительность self-join. На больших объёмах это переписывают через оконные функции или asof-join, идея не меняется.

Для MLE: именно эту модель и её описание мы видели на слайде про docs. Круг замкнулся: ML-свойство признака зафиксировано и в SQL, и в документации.

Осторожно: `left join`, а не `inner`. У первого заказа продавца истории нет — признак должен стать NULL, а сам заказ обязан остаться в выборке. `inner join` тихо выбросил бы всех новых продавцов, а это как раз самый рискованный сегмент.

Переход: «Мы дошли до края зоны ответственности dbt. Проговорим границу явно».

[~1.5 мин] Главное: dbt отвечает за слой трансформации данных и признаков. Всё, что про модель, — вне его.

Рассказ: прочитать оба столбца. Слева — то, что dbt делает хорошо и за что его стоит брать. Справа — то, чего он не делает и делать не должен: обучение, трекинг экспериментов, реестр моделей, сервинг, мониторинг качества модели.

Переход: «Второй нюанс — про то, чем feature mart не является».

Нюанс 2: offline feature table ≠ online feature store

  • mart_delivery_features — отличный offline feature layer
  • Он же источник обучающей выборки и батч-инференса
  • Но это ещё не online feature store
  • Нет low-latency доступа по ключу за единицы миллисекунд
  • Нет гарантии совпадения online- и offline-расчёта признака
  • Нет отдельного реестра признаков с версиями и владельцами

─────────────────       ─────────────────
offline features        online serving
training dataset        p99 < 10 ms
батч-инференс           point lookup

lineage и тесты         online/offline
                        consistency

[~1.5 мин] Главное: витрина в ClickHouse закрывает offline-часть feature store и не закрывает online-часть.

Рассказ: сказать прямо: для очень многих задач offline-части достаточно. Батч-скоринг раз в сутки, еженедельный пересчёт рекомендаций, аналитические ML-задачи — там online-хранилище не нужно вовсе, и заводить Feast ради галочки не стоит.

Online-хранилище нужно, когда признак требуется по ключу за миллисекунды в момент запроса пользователя.

Для MLE: ключевой риск при переходе к online — online/offline consistency. Тот же признак, посчитанный двумя разными путями, почти гарантированно разойдётся. Это и есть training/serving skew, только теперь на уровне инфраструктуры.

Пример: если Olist-модель отвечает на вопрос «успеет ли заказ» прямо в момент оформления, `seller_avg_delay_90d` нужен за миллисекунды — и тогда нужен online-слой. Если прогноз считается ночью для всех вчерашних заказов — не нужен.

Осторожно: не говорить, что «dbt заменяет feature store». Он закрывает часть задач, и честнее это назвать явно.

Переход: «Третий вопрос, который всегда задают: а Python внутри dbt можно?»

Python-модели в dbt: escape hatch, а не замена SQL

  • Поддержаны на Snowflake (Snowpark), Databricks (PySpark), BigQuery (BigFrames)
  • ClickHouse и Postgres Python-моделей не дают — это ограничение адаптера
  • Модель — функция model(dbt, session), возвращает один DataFrame
  • ref() и source() доступны через объект dbt
  • Ограничения: нет view/ephemeral, print() не виден, импорт между моделями невозможен
models/marts/mart_seller_cluster.py
def model(dbt, session):
    dbt.config(materialized="table")

    orders = dbt.ref("int_order_level")

    # то, что действительно
    # неудобно выразить в SQL
    from sklearn.cluster import KMeans
    pdf = orders.to_pandas()
    pdf["cluster"] = KMeans(
        n_clusters=5, n_init=10
    ).fit_predict(
        pdf[["distance_km", "item_count"]]
    )
    return pdf

[~1.5 мин] Главное: Python в dbt — это аварийный выход, а не альтернативный основной путь.

Разбор кода: три строки. `def model(dbt, session)` — обязательная сигнатура. `dbt.ref(...)` — тот же граф зависимостей, что и в SQL: Python-модель встаёт в общий DAG. `return pdf` — модель обязана вернуть ровно один DataFrame.

Не разбирать: параметры KMeans, они тут для правдоподобия.

Для MLE: и сразу трезвая оговорка. На ClickHouse, с которым мы работаем в этом курсе, Python-моделей нет — это ограничение адаптера, а не настройка. Поддержка есть у Snowflake, Databricks и BigQuery. Проверяйте страницу конфигурации вашего адаптера, прежде чем закладывать это в архитектуру.

Осторожно: несколько практичных ограничений. `print()` в логах dbt не появится — код исполняет платформа, а не dbt. Функции из одной Python-модели нельзя импортировать в другую. И материализация только `table` или `incremental` — ни `view`, ни `ephemeral`.

Переход: «Если Python-моделей нет, а расширить dbt хочется — есть отдельный проект».

[~0.3 мин] Главное: самый длинный блок лекции — соединяем dbt с обучением.

Ответ по схеме: у dbt нет и не должно быть представления о том, что до него отработала загрузка, а после него надо обучить модель, посчитать метрики и положить артефакт в реестр. dmp-af: dbt-first оркестрация на Airflow

  • Философия обратная: не Airflow с dbt внутри, а dbt, из которого генерируется Airflow
  • Domain-driven: модели разных доменов разъезжаются по отдельным DAG-ам
  • Расписание описывается в конфигурации dbt-моделей, а не в коде DAG
  • Каждая модель — отдельная задача Airflow, зависимости сохраняются между доменами
  • Date interval Airflow можно использовать внутри dbt-трансформаций
  • Целевой случай — большие доменно-организованные dbt-проекты

from airflow.decorators import dag, task
from cosmos import DbtTaskGroup, ProjectConfig, RenderConfig

@dag(schedule="0 3 * * *", catchup=False, tags=["olist", "ml"])
def olist_delivery_model():

    wait_raw = FileSensor(task_id="wait_for_olist_raw", filepath=RAW_MARKER)

    transform = DbtTaskGroup(            # весь dbt-граф раскроется в задачи
        group_id="dbt_olist",
        project_config=ProjectConfig(dbt_project_path=DBT_DIR),
        profile_config=PROFILE,
        render_config=RenderConfig(select=["tag:features"]),
    )

    @task
    def train():                         # обучение — уже НЕ dbt
        df = read_features("analytics.mart_delivery_features")
        return fit_and_log(df)           # метрики → tracking

    @task.short_circuit
    def evaluate(run_id: str) -> bool:   # барьер качества модели
        return metrics(run_id)["roc_auc"] >= baseline()

    run = train()
    wait_raw >> transform >> run
    evaluate(run) >> register(run)

[~2.5 мин] Главное: архитектурная идея важнее синтаксиса. Задача этого слайда — показать, что весь dbt-слой занимает один объект, а не тридцать операторов.

Разбор кода: четыре точки. Первая — `DbtTaskGroup`: три конфига, и весь граф моделей раскрылся в задачи. Никаких `stg_orders >> int_order_level` руками. Вторая — `@task def train()`: обучение читает готовую витрину и живёт вне dbt. Третья — `@task.short_circuit` на `evaluate`: если метрика хуже baseline, ветка ниже пропускается, и модель не регистрируется. Четвёртая — последние две строки: зависимости между крупными этапами.

Не разбирать: `PROFILE`, `RAW_MARKER`, тело `fit_and_log` — это заглушки.

Для MLE: обратите внимание на симметрию. Барьер данных — внутри `transform`, его делает `dbt build`. Барьер модели — снаружи, его делает `short_circuit`. Каждый отказ останавливает пайплайн в своей точке.

Инструмент не влияет на результат — на выходе всё равно SQL в git, — но сильно влияет на скорость правок. Голый CLI честен и переносим, однако редактор не знает про ваши модели: нет автодополнения `ref`, нет подсказки по колонкам, ошибка находится только при запуске.

Локально это лечится двумя разными расширениями, и их легко перепутать. Power User от Altimate — сторонний open-source-пакет поверх обычного dbt Core: автодополнение, скомпилированный SQL, preview запроса, column lineage, AI-функции по ключу. Официальное расширение dbt Labs — другое: оно приносит движок Fusion и работает именно с ним, а не с dbt Core 1.x. Это первое, что стоит проверить, если расширение «не видит» проект.

Браузерные среды дают среду, планировщик, CI и документацию одним куском, но заточены по-разному. dbt Studio (бывшая dbt Cloud IDE) — родная среда dbt Labs: автодополнение моделей и колонок, встроенные sqlfmt и SQLFluff, просмотр DAG, git-диффы и разрешение конфликтов, ассистент прямо в редакторе. Paradime позиционируют как «Cursor для данных»: агент собирает модель и документацию, открывает PR и тянет контекст из Jira, Confluence и таблиц, а на каждый PR показывает column-level lineage до дашбордов BI. Datacoves — managed-платформа на Airflow с VS Code в браузере и упором на корпоративное управление доступом.

Отдельная строка — SqlDBM: это не редактор, а визуальный моделер. Вы рисуете ER-модель, а он генерирует dbt-YAML (колонки, описания, типы, тесты и freshness) и умеет пушить его прямо в репозиторий проекта. Полезно там, где модель данных согласуют с архитекторами до написания SQL. Общая плата за платформенные варианты одна — привязка к вендору: цена за место, лимиты и вопрос «как отсюда уехать», который стоит задать до внедрения, а не после.

Fusion и dbt Core v2.0: движок переписан на Rust

  • Fusion — движок на Rust: он разбирает SQL, а не только подставляет Jinja
  • Мгновенный парсинг, ошибки до запуска, IntelliSense в VS Code и Cursor
  • dbt Core v2.0 собран на том же коде и открыт под Apache 2.0 (alpha, июнь 2026)
  • Артефакты в Parquet вместо JSON: метаданные читаются запросом, а не разбором файла
  • Ветка 1.latest живёт дальше — обновляться прямо сейчас никто не обязан
📚 Материалы: About Fusion · dbt Core v2 is here

Главная новость экосистемы: dbt переписали на Rust. Движок Fusion — это наследие покупки SDF, и его принципиальное отличие в том, что он понимает SQL, а не только шаблонизирует текст. Отсюда мгновенный парсинг больших проектов, ошибки, которые видно до запуска в хранилище, и осмысленный IntelliSense в редакторе.

В июне 2026 dbt Labs выпустили dbt Core v2.0 — alpha, собранная на том же коде и открытая под Apache 2.0; в открытый доступ уехало то, что раньше жило в репозитории dbt-fusion. Отдельно стоит запомнить смену формата артефактов: вместо гигантского `manifest.json` — Parquet, который читается запросом. Именно поэтому обновлённые доки и агенты работают с метаданными быстро.

Макросы в проекте: диспетчеризация и границы

  • Макросы живут в macros/ и доступны всему проекту без импортов
  • adapter.dispatch выбирает реализацию по адаптеру: default__ и clickhouse__
  • Так один и тот же проект компилируется под несколько СУБД
  • Макросы описываются в YAML наравне с моделями — иначе их никто не найдёт
  • Граница простая: макрос ради двух строк вредит читаемости больше, чем помогает
macros/date_diff.sql — один вызов, разные СУБД
{% macro date_diff_days(a, b) %}
  {{ return(adapter.dispatch('date_diff_days')(a, b)) }}
{% endmacro %}

{% macro default__date_diff_days(a, b) %}
  datediff('day', {{ a }}, {{ b }})
{% endmacro %}

{% macro clickhouse__date_diff_days(a, b) %}
  dateDiff('day', {{ a }}, {{ b }})
{% endmacro %}
📚 Материалы: adapter.dispatch

Три вещи, которые отличают проектные макросы от случайных вставок. Первое — место: каталог `macros/`, откуда они видны всему проекту без импортов; пакеты (`dbt_utils.star`) вызываются с префиксом, и префикс здесь полезен — по нему видно, чей код исполняется.

Второе — диспетчеризация. `adapter.dispatch` выбирает реализацию по текущему адаптеру: `default` работает везде, `clickhouse` подменяет её на ClickHouse. Это тот самый механизм, которым пакеты добиваются переносимости, и он же нужен вам, если проект компилируется под несколько хранилищ. Ровно его требует настроить `dbt_project_evaluator` — блок `dispatch`, который мы видели на слайде про него.

Третье — описание. Макрос без документации в YAML не найдёт никто, включая вас через полгода; он просто будет написан заново рядом. И честная граница: макрос оправдан, когда логика повторяется и меняется вместе. Если это две строки в одном месте — оставьте SQL: скомпилированный текст читать проще, чем цепочку из четырёх макросов, каждый из которых вызывает следующий.

Два словаря про одно и то же. Medallion (bronze / silver / gold) пришёл из мира Databricks и хорош тем, что его понимают за минуту. Классическая EDW-раскладка подробнее: `raw` и `landing` для сырого, `stg` для приведения к типам, `core` или `DDS` для бизнес-сущностей, `rep` и BI-витрины наверху. Спорить, какой словарь правильный, бессмысленно — важно, чтобы в команде он был один.

Что действительно важно и одинаково в обоих: правило одного направления. Слой читает только то, что ниже, и никогда не тянет из соседа сбоку и не смотрит вверх. Внутри dbt это выражается буквально — `sources` для сырого, `staging` один к одному к источнику, `intermediate` для бизнес-логики, `marts` для витрин.

Отдельно про два места, которые часто забывают. Feature store — не отдельная вселенная, а такой же gold-слой, только потребитель у него ML, а не дашборд. А песочница аналитика (`ad-hoc`, `DA`) должна жить в своей схеме вне основного графа. Как только ad-hoc-модель становится источником для витрины, слои перестают работать, и починить это позже дороже, чем не допустить.

dbt_project_evaluator: правила слоёв под контролем

  • Шесть групп правил: граф, тесты, документация, структура, производительность, governance
  • Ловит нарушения ровно тех договорённостей о слоях, что мы только что проговорили
  • Результат — не отчёт в консоли, а fct_-модели и тесты: их можно завалить в CI
  • int_all_dag_relationships отдаёт весь DAG таблицей — свои проверки пишутся SQL-ом
  • Исключения оформляются seed-ом, а правило остаётся включённым для всех остальных

Слои и правила из предыдущих слайдов держатся ровно до первого дедлайна: кто-нибудь сходит `join`-ом прямо в `source` мимо staging, и через полгода так сделает половина проекта. dbt_project_evaluator — это автоматическая проверка тех самых договорённостей.

Он проверяет шесть групп правил: устройство графа (join в source мимо staging, rejoin уже соединённых сущностей, fanout, модели без потомков), покрытие тестами и документацией, структуру (именование и раскладка по каталогам), производительность (цепочки вьюх там, где нужна таблица) и governance. Ставится как обычный пакет; для ClickHouse и ряда адаптеров дополнительно нужен блок `dispatch`.

Ключевая деталь — формат результата. Это не текстовый отчёт, который все прочитают один раз: пакет собирает `fct_`-модели с нарушениями и обычные dbt-тесты поверх них, поэтому его можно поставить в CI и завалить сборку. Таблица `int_all_dag_relationships` отдаёт весь граф в виде строк, и по ней пишутся собственные правила. А если нарушение осознанное, оно оформляется исключением через seed — правило при этом продолжает действовать для всех остальных моделей, а не отключается целиком.

Data Vault и AutomateDV

  • Hub — бизнес-ключ, Link — связь между ключами, Satellite — атрибуты и их история
  • Новый источник добавляется рядом, а не переписывает существующие таблицы
  • AutomateDV собирает SQL по метаданным, staging считает хеш-ключи и hashdiff
  • Satellite обычно incremental: история пишется вставками, без обновлений
  • Цена подхода — много таблиц и обязательный слой витрин поверх для BI

     src_source='RECORD_SOURCE',

-- руками он не пишется

Data Vault решает конкретную боль: источников много, они меняются, а переделывать схему каждый раз дорого. Модель раскладывается на три вида таблиц — Hub (бизнес-ключ), Link (связь) и Satellite (атрибуты с историей). Ключевое свойство: новый источник добавляется рядом новой сателлит-таблицей, а существующие не переписываются, и грузиться всё это может параллельно.

Руками такой SQL никто не пишет. AutomateDV (бывший dbtVault) генерирует его по метаданным: в staging-слое считаются хеш-ключи и `hashdiff`, а модель хаба или сателлита — это вызов макроса с описанием полей. Сателлиты обычно `incremental`, потому что история пишется вставками, а не обновлениями.

Честно про цену. Таблиц становится в разы больше, читать их напрямую невозможно, поэтому поверх обязательно нужен слой витрин (тот самый Kimball с фактами и измерениями) — иначе BI просто не поедет. Поэтому Data Vault оправдан там, где источников много и они живут своей жизнью; для одного продуктового источника это оверинжиниринг.

Права доступа: что делает dbt, а что DBA

  • grants — структурированный конфиг: dbt выдаёт права сам после сборки модели
  • Плюс перед привилегией добавляет получателей, без плюса — заменяет список
  • На sources, схемы и сам кластер прав dbt не выдаёт — это остаётся за DBA
  • Роли разделяем: dev пишет в свою схему, прод-роль ходит только в прод
  • Пароли и ключи — через env_var в profiles.yml, а не строкой в репозитории
dbt_project.yml — гранты как конфиг, а не post-hook
models:
  my_project:
    marts:
      +grants:
        select: ['analyst', 'bi_service']

# без плюса — список заменяет существующий
# с плюсом (+select) — добавляет к нему
# применяется после сборки каждой модели
📚 Материалы: grants

До версии 1.2 права раздавали `post-hook` с самописным `GRANT`. Теперь есть конфиг `grants`: вы объявляете, кому что можно, а dbt сам применяет права после сборки модели — на нужном диалекте и без ручного SQL. Работает на моделях, seed-ах и снапшотах, объявляется в `dbt_project.yml`, в YAML-свойствах или прямо в модели.

Одна деталь ломает больше всего сборок: плюс перед привилегией. `select:` — заменить список получателей целиком, `+select:` — добавить к унаследованному. Перепутали — и вы молча отобрали доступ у половины BI.

Важнее понять границу. dbt управляет правами только на то, что создал сам. Доступ к сырым источникам, права на схемы, роли и пользователи в ClickHouse или Snowflake — это по-прежнему работа DBA, и dbt туда не лезет. Практическое правило: у разработчика своя схема и своя роль, у прода — отдельная, с записью только в прод. А пароли и ключи в `profiles.yml` подставляются через `env_var`: профиль в репозитории должен быть безопасен для чтения любым, у кого есть доступ к коду.

Пакеты: версии, обновление и риски

  • Версия пинится диапазоном или тегом — «последняя» ломает сборку в чужой день
  • package-lock.yml коммитим, каталог dbt_packages/ — нет
  • Пакет — это чужой код в вашем проекте, его макросы могут переопределить ваши
  • Транзитивные зависимости конфликтуют по версиям, dbt deps скажет об этом сразу
  • Обновление пакета — отдельный MR с прогоном тестов, а не «заодно с фичей»
packages.yml — версии пинятся, dbt_packages не коммитим
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.3.0", "<2.0.0"]

  - package: calogica/dbt_expectations
    version: 0.10.4

  - git: https://github.com/org/dbt-internal.git
    revision: v1.2.0      # тег, а не ветка

# dbt deps  -> dbt_packages/  (в .gitignore)
# package-lock.yml коммитим: он фиксирует,
# что реально скачалось
📚 Материалы: packages.yml · dbt deps

Пакеты — это зависимости, и обращаться с ними надо как с зависимостями кода. Версию всегда пиньте: диапазоном (`>=1.3.0, <2.0.0`) или точным значением; для приватных пакетов из git указывайте тег, а не ветку, иначе сборка меняется в тот день, когда кто-то запушил в main чужого репозитория. С dbt 1.7 рядом появляется `package-lock.yml` — его коммитят, потому что он фиксирует то, что скачалось на самом деле, а сам каталог `dbt_packages/` в git не хранят: он воспроизводится командой `dbt deps`.

Риск, о котором забывают: макросы пакета живут в одном пространстве имён с вашими. Пакет может переопределить макрос, а два пакета — потребовать несовместимые версии третьего; `dbt deps` сообщает о конфликте, но выбор остаётся за вами. Поэтому вызов через префикс (`dbt_utils.star`) — не формальность, а способ понимать, чей код исполняется.

И организационное правило: обновление пакета — это отдельный merge request с прогоном тестов и чтением changelog. В major-версиях пакеты меняют сигнатуры макросов, и такая правка, приехавшая «заодно» с продуктовой фичей, превращает разбор падения в археологию.

Второй эшелон — то, что ставят под конкретную задачу, а не в каждый проект. dbt_profiler считает профиль колонок (доля NULL, уникальность, границы) и умеет класть его в документацию: это первое, что делаешь с незнакомым источником. dbt_external_tables описывает файлы в объектном хранилище как обычные `sources`, избавляя от ручного DDL. dbt_artifacts складывает метаданные прогонов в витрины — из них потом растут дашборды «сколько шла сборка» и «что падает чаще всего».

Обратите внимание на пометку pip у последних двух. `dbt-score` и `dbt-colibri` — не dbt-пакеты: они не ставятся через `packages.yml` и `dbt deps`, а живут как отдельные python-утилиты рядом с проектом и читают его артефакты. Это другой способ подключения и другое место в CI.

dbt-score от Picnic оценивает метаданные модели по правилам и выдаёт балл 0–10 — на этом удобно строить гейт «описания и владельцы обязательны». dbt-colibri собирает column-level lineage из уже существующих артефактов и рисует локальный дашборд. Получается тот самый lineage по колонкам, за который обычно платят платформе, — ценой ещё одного шага в пайплайне.

Пакеты в CI и проде: воспроизводимость

  • dbt deps — шаг пайплайна, а не то, что каждый делает у себя руками
  • Кэш dbt_packages экономит минуты, package-lock.yml гарантирует те же версии
  • Приватный пакет тянут по git+тегу с токеном из переменной CI, не из URL в репозитории
  • В docker-образ для прода пакеты кладут на этапе сборки, а не в рантайме
  • Обновление пакетов — отдельный MR со своим прогоном, а не сюрприз в ночном ране
.gitlab-ci.yml — deps как шаг сборки, а не ручное действие
dbt_build:
  image: python:3.12
  cache:                     # не тянем пакеты каждый раз
    key: dbt-deps-$CI_COMMIT_REF_SLUG
    paths: [dbt_packages/]
  before_script:
    - pip install -r requirements.txt
    - dbt deps               # читает package-lock.yml
  script:
    - dbt build --target ci

# приватный пакет: токен из переменной CI,
# в packages.yml — только ссылка и тег
📚 Материалы: dbt deps

Пакеты ломают сборку не в разработке, а в CI и проде — потому что там никто не помнит, что нужно выполнить `dbt deps`. Правило простое: deps — это шаг пайплайна. Рядом стоят две оптимизации: кэш каталога `dbt_packages` (минуты на каждом прогоне) и `package-lock.yml`, который гарантирует, что в CI и на ноутбуке приехало одно и то же.

Приватные пакеты — отдельная тема безопасности. В `packages.yml` хранится только ссылка и тег; токен приезжает переменной окружения CI и никогда не коммитится в URL. Это ровно тот случай, когда «работает и так» означает утечку в истории git.

В проде порядок тот же, но жёстче: пакеты ставятся на этапе сборки образа, чтобы контейнер не ходил в интернет в рантайме, а обновление пакета оформляется отдельным merge request со своим прогоном тестов. Иначе разбор ночного падения начинается с вопроса «а что у нас вообще изменилось», на который нет ответа.

Snapshots и docs: история + смысл поля

  • Snapshot реализует SCD2: сохраняет версии бизнес-сущности во времени
  • unique_key определяет объект, а check_cols — что считать изменением
  • dbt добавляет интервалы валидности, чтобы запросить «состояние на дату»
  • Docs-блок хранит одно описание и подставляется в несколько мест
  • Документация становится частью ревьюируемого кода

Snapshot — это механизм историзации SCD2 для случаев, когда источник хранит только актуальную строку. Здесь id определяет клиента, а изменение name или status создаёт новую версию. Материализованные представления: ClickHouse

  • В ClickHouse MV — не кэш, а триггер на вставку: агрегат считается в момент INSERT
  • Приёмник обычно AggregatingMergeTree, и GROUP BY совпадает с его ORDER BY
  • catchup=True сначала догоняет историю, потом создаёт саму MV
  • Refreshable MV пересчитывает всё по расписанию — можно JOIN, но свежесть ниже
  • В dbt это materialized_view: одна модель описывает и MV, и таблицу-приёмник

    engine='AggregatingMergeTree()',
    order_by='(day, country)',

select toDate(ts) as day, country,
       countState()       as visits,
       uniqState(user_id) as users
from {{ source('raw', 'events') }}

Главное недоразумение: в ClickHouse материализованное представление — это не кэш запроса, а триггер на вставку. Данные приезжают в исходную таблицу, MV в этот момент считает свою часть агрегата и кладёт результат в таблицу-приёмник. Читаете вы приёмник, и он всегда актуален по мере вставок.

Отсюда два правила. Приёмник берут AggregatingMergeTree (или SummingMergeTree), а состояния пишут через `-State`-функции — `countState`, `uniqState`; при чтении их сворачивают `-Merge`. И `GROUP BY` в MV должен совпадать с `ORDER BY` приёмника, иначе строки не схлопнутся и таблица распухнет.

В dbt это отдельная материализация `materialized_view` адаптера ClickHouse: одна модель описывает и представление, и приёмник, а `catchup=True` догоняет историю перед созданием. Отдельно стоят refreshable MV — они периодически пересчитывают весь результат, поэтому поддерживают JOIN-ы. Выбор простой: инкрементальная MV — когда нужна свежесть на вставке; refreshable — когда нужны сложные соединения и можно потерпеть задержку.

Микробатчинг: инкремент окнами времени

  • dbt сам фильтрует upstream-модели, у которых объявлен event_time

📚 Материалы: microbatch

Обычная инкрементальная модель делает один большой запрос на всю дельту. Пока данных мало — нормально; на бэкфилле за год это один запрос на миллиарды строк, который падает по памяти на девяносто восьмом проценте и начинается сначала.

Стратегия microbatch (dbt 1.9) переворачивает это: модель объявляет `event_time`, `batch_size` и начало истории, а dbt сам режет период на окна и выполняет по запросу на окно. Предикат подставляется автоматически — писать `is_incremental()` и вручную считать `max(order_date)` больше не нужно.

Два следствия, ради которых всё затевалось. Первое: упавший батч перезапускается отдельно, остальные остаются на месте. Второе: `lookback` заставляет пересчитывать несколько прошлых окон, что закрывает вечную проблему опоздавших событий. Плюс dbt автоматически подрезает upstream-модели, у которых тоже объявлен event_time, — граф перестаёт читать лишнее.

Вопрос «умеет ли dbt в стриминг» поставлен неточно. dbt — это генератор SQL и оркестратор графа, у него нет собственного рантайма; непрерывность даёт движок под ним, а dbt описывает, что именно считать.

Практически это выглядит так. В RisingWave модель материализуется как `materialized_view` — потоковая MV, которая обновляется сама по мере прихода событий; `incremental` там просто не нужен, а для выгрузки наружу есть материализация `sink`. В экосистеме Spark ту же роль играют streaming tables поверх Structured Streaming. В обоих случаях `dbt run` — это деплой определения, а не запуск обработки каждую минуту.

Что остаётся за dbt и ради чего его сюда тащат: потоковые определения попадают в git, получают тесты, описания и lineage наравне с батчевыми моделями. Граница проходит по свежести: секунды — стриминговый движок, минуты и часы — микробатчинг из предыдущего слайда, и это дешевле в эксплуатации.

📚 Материалы: Jinja в dbt

Соберём разговор про Jinja в один честный SWOT. Сильная сторона и слабая — это одно и то же свойство, посмотренное с разных сторон: Jinja ничего не знает о SQL. Именно поэтому он работает с любым диалектом и любым движком, и именно поэтому он не может подсказать вам ни колонку, ни тип, ни то, что вы разорвали выражение пополам.

Возможности — там, где логика повторяется и описывается метаданными: пивот по значениям из данных, генерация staging через codegen, хабы и сателлиты AutomateDV, единый проект под несколько СУБД. Всё это без шаблонов пришлось бы писать руками или внешним генератором.

Угрозы начинаются, когда шаблонов становится больше, чем SQL. Проект превращается в программу, которая печатает SQL: отладка идёт через `target/compiled`, а не через чтение модели, и цена каждого следующего макроса растёт. Второй, более медленный риск — направление индустрии: чтобы строить lineage на уровне колонок, движку нужно разбирать SQL, а не склеивать строки. Об этом следующий слайд.

Почему другие движки уходят от шаблонов

  • SQLMesh: макросы правят семантическое представление запроса (SQLGlot), а не текст
  • В его документации претензия прямая — шаблонизатор намеренно ничего не знает о языке, который шаблонизирует
  • Spark SDP: датасеты объявлены кодом (.py или .sql), таблицы в цикле — обычный Python, шаблонного слоя нет
  • Bruin — контрпример: он как раз на Jinja, со своими start_date/end_date, циклами и условиями
  • Уходят не «все», а те, кто строит lineage по колонкам: для этого SQL надо разбирать
одно ограничение — текстом и над разобранным SQL
-- dbt + Jinja: подстановка текста
{% set cutoff = var('cutoff_days', 30) %}
select * from {{ ref('orders') }}
where order_date >= current_date - {{ cutoff }}

-- SQLMesh: макрос над разобранным SQL
@DEF(cutoff, 30);
SELECT * FROM orders
WHERE order_date >= CURRENT_DATE - @cutoff;

Сначала поправка к расхожему тезису: «все уходят от Jinja» — миф. Bruin, один из самых заметных новых инструментов, построен ровно на нём: переменные `start_date` и `end_date`, циклы, условия — знакомая картина. Уходят не все, а те, кому мешает конкретное свойство.

Свойство это — слепота к SQL. У SQLMesh макросы правят семантическое представление запроса, разобранное библиотекой SQLGlot, и поэтому движок сам понимает, подставить ли строковый литерал или идентификатор. В документации претензия сформулирована прямо: шаблонизатор намеренно ничего не знает о языке, который шаблонизирует. Показательно, что Jinja там при этом поддержан — его не запрещают, его понижают в статусе.

Spark Declarative Pipelines решают задачу иначе: там нет шаблонного слоя вовсе. Исходники — `.py` или `.sql`, датасеты объявляются кодом через `pyspark.pipelines`, и если нужно создать двадцать похожих таблиц, это обычный питоновский цикл, а не текст с дырками.

Общий знаменатель — column-level lineage и анализ влияния. Чтобы сказать «эта правка ломает вот эту колонку в вон той витрине», движок обязан разобрать SQL. И то же самое сейчас делает сам dbt: Fusion разбирает SQL и вводит строгую спецификацию языка — та же критика, пришедшая изнутри.

Раньше на этом месте было три слайда сравнения — сведём их в один честный SWOT. Сильные стороны SQLMesh технические и реальные: он разбирает SQL в синтаксическое дерево через SQLGlot, поэтому знает lineage на уровне колонок и отличает ломающее изменение от безобидного. Виртуальные среды делают «свою копию хранилища на ветку» дешёвой, а `plan` показывает влияние правки до применения.

Слабости — не в технике, а вокруг неё: пакетов меньше, статей и курсов меньше, нанимать сложнее, интеграции менее обкатаны. Именно это чаще всего и решает исход спора в команде.

Возможности — там, где нет груза legacy: новый проект, дорогие preview-среды, желание получить impact analysis. Причём переходить целиком не обязательно: SQLMesh умеет запускаться поверх существующего dbt-проекта (следующий слайд). Угрозы — миграция ради миграции, двойной стек, когда половина команды живёт в одном инструменте, а половина в другом, и зависимость от одного вендора. Практический вывод курса: на greenfield SQLMesh стоит рассматривать всерьёз, а работающий dbt-проект переносят только под конкретную боль, которую можно назвать вслух.

Окружения SQLMesh создаёт сам во время `plan`, поэтому хардкодить target в профиле не нужно: профиль указывает на прод, остальное берёт на себя движок.

Честные ограничения тоже стоит назвать. Инкрементальные блоки `is_incremental()` заменяются на sqlmesh_incremental с предопределёнными временными переменными; часть jinja-методов (`debug`, обход `graph.nodes`) недоступна; у snapshots не поддержан `invalidate_hard_deletes=False`; типы seed-колонок иногда приходится указывать явно. Поэтому реалистичный сценарий — не «переезд в пятницу», а параллельный запуск на копии проекта: увидеть plan, оценить impact analysis и уже потом решать.

Декларативные трансформации: ещё четыре подхода

  • Bruin — один CLI для ingestion, SQL/Python assets, quality checks и lineage в repo
  • Spark Declarative Pipelines (SDP) — SQL/Python для batch и streaming-графов
  • Databricks Lakeflow — managed-пайплайны: flows, streaming tables, materialized views
  • Snowflake Dynamic Tables — SELECT + TARGET_LAG; платформа сама ведёт refresh и порядок DAG
  • Выбор: portable dbt/SQLMesh/Bruin или нативные возможности конкретной платформы

Тренд шире одного dbt: команды всё чаще описывают желаемый набор данных и зависимости, а не последовательность низкоуровневых задач. Bruin объединяет ingestion, SQL/Python-преобразования, quality checks и lineage в репозитории — полезно, когда хочется меньше разрозненных инструментов.

В Spark-экосистеме Spark Declarative Pipelines описывает batch и streaming-пайплайны в SQL или Python. Databricks Lakeflow — управляемая реализация этого подхода: платформа анализирует зависимости и оркестрирует flows, streaming tables и materialized views. Это естественно для Delta/streaming-нагрузок, но сильнее привязывает решение к платформе.

В Snowflake Dynamic Tables позволяют определить результат SQL-запросом и TARGET_LAG; Snowflake сам поддерживает порядок refresh и, где возможно, incremental processing. Для процедурной логики, точного cron или сложного MERGE остаются streams/tasks. dbt выигрывает переносимостью и экосистемой, нативные средства — меньшим количеством операционного кода внутри своей платформы. Современный стек часто сочетает эти подходы, а не выбирает ровно один.
