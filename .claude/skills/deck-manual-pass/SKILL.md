Деки генерируются из `content/*-content.yml`, но по готовой `.pptx` регулярно идёт ручной
проход, после которого работа продолжается генератором. Главное, что надо помнить и сказать
вслух пользователю:

> **Правка, сделанная только в `.pptx`, умирает на следующей сборке.** Она переживает
> пересборку, только если её вернули в источник.

Полный разбор цикла — `docs/deck-manual-pass.md`. Здесь — как действовать.

## Первым делом: спасти файл

Рукописная правка — **не артефакт**, пересобрать её нечем, и лежит она в одном экземпляре.
До любого анализа:

```bash
git status --short | grep -i man          # untracked *-man.pptx = под угрозой
git add data/source/manual/... && git commit
```

`data/drafts/` отслеживается, но файлы туда попадают untracked; `.tmp/build/` целиком в
`.gitignore`. `git worktree remove` и `just clean` уносят и то, и другое молча. Реальный
случай 2026-09-01: 9.8 МБ ручной работы существовали только на диске и только в открытом
окне PowerPoint.

Постоянное место и соглашение об именах (`-man` / `+man`) — `data/source/manual/README.md`.

## Куда что возвращать

| Правка | Как вернуть |
|---|---|
| шрифты, отступы, геометрия, обводка | `just preza-merge-propose` → ревью правил → `just preza-merge-apply` |
| текст слайда, буллеты, заголовки, заметки | руками в `content/*-content.yml`, точечно `just preza-slides` |
| новые/удалённые/переставленные слайды | руками `just preza-slides insert/remove/move` — графт слайдов между `.pptx` намеренно не реализован |
| картинки | `just preza-images sync` — снятое руками помечается `manual-removed` и обратно не ставится |
| правки в HTML/PDF | не возвращаются: профиль описывает геометрию `.pptx` |

Лента `preza-merge` переносит **форматирование, а не содержание** — это её объявленная
граница, а не недоделка. Не обещать пользователю, что она перенесёт текст.

## Порядок при большом объёме правок

1. `just preza-merge-propose` — трёхсторонний дифф выпишет всё изменившееся. Что не попало
   в правила форматирования, то и есть список ручного возврата.
2. Форматирование — принять правила, `just preza-merge-apply`.
3. Содержание и структуру перенести в content-YAML, сверяясь со списком из п. 1.
4. `just preza-merge-verify` — структурный остаток против форка.
5. Пересобрать; глазами проверить страницы, которых правка касалась.

## Что проверить, прежде чем сказать «готово»

* `*-man.pptx` в `git ls-files`, а не только на диске.
* Ручная версия не новее последнего изменения `content/*-content.yml` — иначе часть работы
  ещё не возвращена.
* `deck.format` в content-YAML указывает на профиль, который применили.
* Пересборка прошла, и правка видна в новой версии.

## Чего не делать

* Не править собранную деку на месте — она помечается read-only намеренно; работать с копией.
* Не откладывать коммит ручного файла «до конца разбора».
* Не предлагать пересобрать деку, пока ручная работа не возвращена: пересборка её затрёт.
* Не звать `apply --backend graft` — падает `NotImplementedError` по проекту.
* Не путать со скиллом `preza-graft`: тот сводит ДВЕ ручные линии одной деки между собой.
  Если правили в PowerPoint две версии сразу и непонятно, какая актуальна, — сначала он,
  и только потом возврат в генератор по этому скиллу.
