Правило владельца от 2026-09-01, действует во всех репозиториях семейства:

> Убирая файлы — не удалять, а переносить в `../.recyclebin`. Исключение: файл, чьё
> содержимое побайтово совпадает с уже сохранённой копией, — такой можно удалить, но
> история удалений ведётся всегда.

## Инструмент

```bash
just recycle .tmp/render-pdf                                   # перенести в корзину
just recycle --dup-of data/source/manual/x.pptx data/drafts/x.pptx   # удалить как дубль
just recycle --dry-run <путь>                                  # показать, что будет
```

`scripts/recycle.sh` сам заводит корзину и журнал, если их нет. Путь переопределяется
переменной `RECYCLEBIN`; значения по умолчанию — в `settings/config.yml` → `recyclebin`.

## Что скрипт проверяет до необратимого шага

| Проверка | Почему |
|---|---|
| файл открыт другим процессом (`lsof`) | удаление выдернет документ из-под редактора; 2026-09-01 `git rm` снёс .pptx, открытый в PowerPoint |
| `--dup-of`: sha256 обеих сторон | «дубль» без сверки — это не дубль, а догадка |
| `--dup-of` не указывает на сам удаляемый файл (путь + inode) | иначе файл сверяется сам с собой, сверка всегда проходит, и удаляется единственный экземпляр — так 2026-09-01 и вышло |
| `--dup-of` на каталогах: слепок «относительный путь + sha256» по всем файлам | `shasum` на каталоге молчит, обе стороны выходили пустыми и «совпадали» — каталог удалялся без единой сверки. Разнотипная пара (файл против каталога) и симлинк/сокет внутри — отказ, сверка была бы неполной |
| источник и корзина на одном томе (`stat -f %d`) | `mv` между томами не атомарен: прерывание оставит половину и никакого оригинала. На разных — копия → сверка sha256 → удаление |

## Журнал

`../.recyclebin/.history.csv`, колонки:
`ts_utc,action,path_from,repo,sha256,size_bytes,kept_at,reason,actor`.
`action` ∈ `moved` | `deleted-duplicate` | `untracked-duplicate` (убран из ветки,
файл оставлен на диске). Журнал ведётся и для переносов — чтобы «а куда делось» решалось
чтением одного файла, а не археологией по веткам.

## Почему не «восстановим из git»

Это верно только пока цел коммит. Ветки сводят, переименовывают и удаляют вместе с
worktree — за один день 2026-09-01 ветка `worktree-preza-dbt-v4-0-2` была создана, удалена,
пересоздана и удалена снова. Под `git-lfs` указатель в истории остаётся, а объект уезжает
в GC вместе с последним ref. И отдельно: заигнорированные каталоги (`.tmp/build/`,
`data/generated/`) не видит ни `git status`, ни проверки `worktree_land.sh` — оттуда файл
исчезает молча. Именно там в тот день час ручной правки деки прожил вне git и уцелел
случайно.

## Границы

Скрипт не чистит корзину и не знает про срок хранения — разрастание корзины решает человек.
Он не заменяет `git rm --cached`: если надо убрать файл ИЗ ВЕТКИ, оставив на диске (файл
открыт, или это рабочая копия пользователя), это другая операция, и в журнал она пишется
как `untracked-duplicate`.

Соседние ленты: `worktree-land` (снос worktree — его `remove` обязан идти через это правило),
`preza-merge` (правки ревьюера), `workstation-bootstrapper` (всё закоммичено и запушено).
