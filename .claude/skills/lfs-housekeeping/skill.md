Здесь два репозитория под `git-lfs` — курсовой `MLInside-course` (деки, PDF, архивы) и
`../.recyclebin`. В обоих вес держат НЕ git-объекты, и `git gc` в них почти бесполезен.

## Сначала померить, потом чистить

```bash
du -sh .git .git/lfs .git/objects
```

2026-09-02 в корзине: `.git` 113 МБ, из них `.git/lfs` 113 МБ, `.git/objects` 304 КБ.
`git gc --prune=now` освободил 232 КБ — то есть ровно ничего. Вывод: если `.git/lfs`
сопоставим с `.git`, `gc` не тот инструмент, и запускать его «чтобы ужать» бессмысленно.

## Что реально освобождает место

```bash
git lfs prune --dry-run            # сколько снимется, ничего не делая
git lfs prune --verify-remote      # снять, проверив КАЖДЫЙ объект на удалёнке
```

`--verify-remote` обязателен. Без него `prune` полагается на своё представление о том, что
объект запушен; с ним он идёт на сервер и убеждается, что копия там есть, ДО локального
удаления. Цена — сетевые запросы, выгода — невозможность стереть единственный экземпляр.

Что `prune` НЕ трогает по построению: объекты, нужные рабочему дереву и текущим ref-ам;
объекты «недавних» коммитов и веток; объекты незапушенных коммитов; объекты, нужные другим
worktree того же репозитория. То есть удаляется только то, у чего копия точно есть ещё где-то.

Результат в корзине: 30 локальных объектов, 1 оставлен, 29 сверены с сервером и удалены —
113 МБ → 428 КБ, `git fsck` молчит, история и рабочее дерево целы.

## Ловушка: не проверяйте обратимость через `lfs fetch --all`

Соблазн после чистки убедиться, что объекты вернутся, — и запустить `git lfs fetch --all`.
Он вернёт ВСЕ объекты и отменит чистку: 428 КБ снова превращаются в 116 МБ, и prune надо
делать заново. Проверять обратимость надо либо одним конкретным объектом
(`git lfs fetch origin main --include=<путь>`), либо просто доверять `--verify-remote`,
который для того и существует.

## Порядок для «почисти репозиторий»

1. `du -sh .git .git/lfs .git/objects` — понять, где вес;
2. `git status` и `git lfs push --dry-run origin <ветка>` — убедиться, что незапушенного нет;
3. `git gc --prune=now` — если вес в git-объектах;
4. `git lfs prune --dry-run`, затем `git lfs prune --verify-remote` — если вес в LFS;
5. `git fsck` и `git status` — история и дерево целы;
6. восстановимость: `git show <коммит>:<файл>` отдаёт указатель с `oid`/`size` — этого
   достаточно, содержимое LFS дотянет с сервера при `checkout`.

## Смежное

Файл, снятый с диска, но оставшийся в истории, — это не потеря: указатель в коммите плюс
объект на сервере восстанавливаются одной командой `git checkout <коммит> -- <файл>`. Но
правило «убирая — не удалять» ([[recyclebin]]) от этого не отменяется: оно про файлы, которых
в истории НЕТ. И наоборот: `lfs prune` безопасен ровно потому, что удаляет только то, что в
истории есть и на сервере лежит.

Сиблинги: `recyclebin` (корзина вместо удаления), `shared-checkout-sync` (общий чекаут),
`workstation-bootstrapper` (воспроизводимость на новой машине).
